# Chat 工具名称与业务结果模板：2026-10-13

本轮已实现工具名称双语显示；后半部分是根据当前源码完成的展示方案分析，尚未实现业务模板整体重构。

后续用户明确要求工具绑定一个模板、模板内部完成展示闭环，缺失/低效查询可补专用接口。新方向和拟改清单见[模板闭环改造计划](./tool-template-redesign-plan-20261013.md)；其中受控只读查询扩展了本文以下分析采用的旧 v1 边界，尚未实现或开放权限。

## 已实现的名称显示

Chat 的折叠工具步骤、展开详情、结果卡片标题及 iframe 可访问标题按当前界面语言显示。覆盖工具搜索、工具详情、主机、Kubernetes、Connector、指标、日志、调用链、仪表盘、告警及离线文件操作。变更预览名称明确包含“预览”，不以工具调用成功表示业务操作已完成。

原始 Tool ID 继续用于路由、权限、审计和历史事件；只在展开详情中作为次要标识保留。客户 MCP 的工具名及未知名称原样显示；历史和 SSE 投影保留已有 source 字段，避免把与自有 ID 同名的外部工具翻译成自有业务。

业务名称来自同一份 Tool Discovery 标题，`scripts/tool-labels` 从实际公开 Registry 生成 API Client 的双语字典，门户不另维护一份业务工具清单。仪表盘目录原来的 `Dashboard get/query` 标题已补齐双语；主机、指标及告警标题同步整理。生成器要求每个公开业务标题包含中英文，并纳入 `argus-dev contracts generate/check`。

历史展示的模板 Hash、数据、Tool ID 和执行状态不因翻译而改变。名称翻译不扩大工具或模板能力。

验证结果：Chat 13 个测试文件、52 项通过，API Client 24 个文件、104 项通过；相关 Go Tool Gateway、Alert、Telemetry、开发命令回归通过。全工作区 Typecheck、i18n、Lint 和样式门禁通过。桌面浏览器中文浅色/英文深色 2/2 通过，覆盖历史结果标题、工具步骤与 iframe 可访问标题；该组是 mock UI + 真实模板源码夹具，不是正式 API/模型业务闭环。记录位于 `artifacts/chat-tool-labels-20261013/`。

第一次浏览器检查发现旧消息聚合形式的 Presentation 没有带入对应 ToolCall 名称；现已按 callId 匹配，避免多工具结果错用第一个名称，并补齐 mock 对 source 的传递。未知名称不再重复追加同一个原始 ID。

全量 Enterprise 套件当前另有两项失败：成员编辑用例仍期待旧行内编辑按钮，授权文件预览用例在并发执行时没有读到预期标题；Chat 专项复跑通过。共享工作区另有列表菜单修改/回滚在进行，本轮保留其内容，没有把这些失败写成全量通过，也未重新构建发布镜像。本轮源代码完成状态与 2026-10-13 先前 `chat-analysis-20261013-r1` 的正式发布状态分别记录。

## 根因：展示模型没有完整表达业务关系

“哪个主机/数据库、什么指标、什么策略、为什么告警”需要同一条结果中的关系链，不能靠页面把 UUID 换成文字就全部解决。

当前 Telemetry Presentation Builder 已查询授权主机/集群名称，并把资源列表放入展示数据。指标模板却主要展示整体资源范围、表达式和序列标签，没有统一的“每条序列对应资源与业务对象”模型。表达式聚合后可能没有 `__name__` 或单个资源标签，不能给聚合结果编造一个具体主机或指标名称。

Alert 的 InstanceState 已保存 `policy_name`、指标、值、阈值和规则快照。模板当前主要使用 `s.name/item.name/s.metric` 和少量状态；范围详情仍直接显示 `page.resource_ids`，虽然 Builder 已有 `data.resources` 名称。这是已有业务事实没有充分用于展示，除了补数据还需要重做投影及布局。

数据库目前不是这里已经接入的独立授权资源类型；查询和展示的资源身份主要是 host/kubernetes_cluster。可以在已授权资源下用真实采集配置或已接收标签识别 PostgreSQL、Redis、数据库实例/名称等业务对象。多实例不能仅凭指标名或主机名区分；缺少实际身份时明确显示“实例未识别”，不让模型猜一个名字。若以后引入独立 Database 资源及权限，需要另行说明资源目录、授权、采集身份和 API 的架构影响。

## 建议的数据和界面分工

保留完整模型结果、模型有界投影、展示数据三个职责。领域服务提供事实，Tool 包内的 Builder 生成版本化展示快照，Tool 模板决定业务布局，通用 Host 只负责隔离、主题/语言、尺寸及已授权导航。无需让 AI 生成 HTML 或选择模板。

展示快照可共享资源名称/类型、查询时间、完整性、来源和公开导航引用；具体业务使用各自的类型，避免把所有结果强塞进一个万能表格。名称解析在服务端按当前企业和资源授权批量完成，不能由模板拿 ID 自行请求 API。展示用名称随当次数据保存；当前授权读取检查继续执行，历史模板不替换成最新源码。

建议的结果结构与层次：

- 指标：资源 → 数据库/服务/设备等已识别对象 → 指标含义 → 数值与单位 → 趋势、时间和完整性。表达式、原始指标名、标签及 ID 放到展开信息。跨资源聚合明确标注为聚合值；单点不画成趋势；单位未知就明确未知。
- 告警事件：策略名 → 规则名 → 资源与指标 → 当前/触发值、阈值、持续时间 → 生命周期、评估健康、处理和静默/抑制。历史触发依据使用当时快照，当前策略修改不改写旧触发条件。
- 主机/集群：名称与状态优先，随后是地址、最近采集、主要资产或工作负载概要，再是必要的来源/版本。列表用紧凑表格，详情用摘要与分区；无采集数据不补假硬件信息。
- 日志/调用链：资源、服务、时间、级别/延迟与摘要优先；日志字段、Trace ID 和详细链路作为次级信息。复用已有日志表、调用链瀑布和 APM 可视化能力。
- 变更预览：目标、影响范围、前后变化和校验结果。确认/取消、审批和执行状态继续属于宿主控件，模板只展示详情。
- 工具搜索、Schema 详情、预算、条件解析、取消及文件操作：优先清晰步骤、可展开参数或已有文件卡片；不为每一步再塞一张大模板。

以下只是说明展示层次的示例数据，不是当前采集事实：

> db-prod-01 · PostgreSQL orders · 活跃连接数 128 · 最近 30 分钟 · 数据截至 15:20
>
> 生产数据库监控 / 连接数过高 · db-prod-01 / orders · 触发值 128，阈值 100，持续 5 分钟 · 活跃告警

两种结果中的资源、对象、指标、单位和时间来自一致的可核验事实；AI 的解释属于会话正文，不能替代这些字段。

## 仪表盘直接渲染：可行，但当前只是简化预览

当前 `internal/dashboard/presentation.go` 已读取 FrozenPlan/封存 Manifest、授权资源名称以及通过 Hash 校验的文件，并在 `templates/query.html` 显示参数和预览。完整 JSON 继续交付 Workspace。因此不能把现状写成“只有 JSON、没有任何图形能力”。

与真实仪表盘页面的差距明确存在：页面使用共享 `ObservationPanel`，接收图型、单位、小数位、图例、display、阈值等配置。Chat 当前只传递 name/signal/type 等基础字段，主要调用简化 timeseries/table/details；单位、阈值、完整布局与其他图型没有完整复用。文件较大或预览预算不足时会省略/截断图形数据并提示。

还有一条独立的触发链路：初次 query 可能产生排队展示，后续 query.get 在已经封存数据时生成完成图形；展示 Builder 以当时实际读到的 Job 状态为准。Query Worker 完成文件交付时，目前只更新状态、写审计和发文件事件，没有自动追加完成态 Presentation。因此模型若未拿到完成态，界面可能仍只有等待展示和 JSON 文件卡片。此结论来自源码路径，不等于已经复现用户这次具体会话。

建议分两个方向完善：

1. 后台封存/交付完成后，通过持久化、幂等的展示事件追加结果，关联 query_job/attempt/来源 ToolCall。不要依赖模型必须补调一次 query.get；也不要直接改写已经保存的历史模板。失败/部分完成同样有明确结果；恢复生成的不同 Attempt 保持独立。具体关联与幂等约束需要设计和真实存储测试。
2. 把共享 `ObservationPanel` 的静态渲染能力接入受隔离 Template Runtime，以通用观测/图表接口消费冻结定义和执行结果；模板仍由 Dashboard Tool 所有，企业门户不增加按 Tool ID 分支的另一套仪表盘。适配或拆出共享渲染核心，保留单位、阈值、图例、格式和图型。关闭编辑、自动刷新和实时查询，保留已加载数据的图例、Tooltip、局部展开等本地交互。修改资源/时间、继续取数或下钻仍通过新消息产生新调用，不扩大 Bridge。

用户看到“参数 + 仪表盘图表 + 结果状态”；AI 使用完整文件分析，JSON 位于文件区供分析/下载。大量数据采用明确标记的有界预览，不能把部分预览包装成全量仪表盘。

## 实施顺序与验收边界

推荐先做指标和告警的关系/单位/来源投影，再做完成态自动展示和共享仪表盘渲染，随后改善资源、日志和调用链的领域布局。先完成这条高频观察链，再扩大模板覆盖数量。

后续验收应覆盖同主机多数据库、多主机同名指标、跨资源聚合、派生单位、策略修改后的旧告警、多规则告警、无数据、部分数据、大结果、撤权和删除、查询完成事件重放、Worker 重启、不同 Attempt、旧/新时间纠正，以及中英 × 明暗桌面显示。用真实 API/存储核对展示与事实一致，再做浏览器与实际模型场景；模板数量和静态样例不是业务闭环证据。

以上方案沿用既定 Tool-owned Template 和 Host 授权边界。独立 Database 资源、模板直接查询/刷新或客户 MCP 任意 HTML 不属于本轮名称修改，也不在本建议中隐式开放。
