## R16：多次用量更新可形成不可能的缓存总量，仍标记完整（P2）

`emitUsage` 只在同一次事件同时提供输入和缓存数时检查缓存不大于输入。`TokenUsage.Observe` 分别覆盖有值的字段；更新输入却省略缓存字段时，旧缓存数继续保留。`CacheComplete` 仅判断字段来源，没有校验最终数值关系。

审计发送的合成流依次包含：

1. 输入 100、缓存输入 80；
2. 正常文本结束，同时更新输入为 50、输出为 8，不再提供缓存字段。

每次更新均通过当前局部校验，最终得到：

```text
input = 50
cached = 80
output = 8
input_source = provider
cached_source = provider
usage_complete = true
cached_usage_complete = true
```

缓存输入本应是总输入的子集。这组互相矛盾的数据却被当作完整实报，可能导致缓存合计和命中率失真。当前模型调用写入路径直接使用这些字段，数据库仅要求缓存数非负，汇总也只检查来源/成功状态；未发现后续的一致性校验。

源码：[逐事件校验与聚合](../../internal/integration/modelprovider/usage.go#L13)、[Chat 用量解析](../../internal/integration/modelprovider/stream.go#L140)、[推理调用落库](../../internal/agent/loop.go#L382)、[压缩调用落库](../../internal/agent/compaction.go#L308)、[用量汇总](../../internal/storage/postgres/queries/model.sql#L56)。

本次实际复现到解析/聚合边界，没有调用真实 Provider，也没有写入真实 ModelCall。该输入模拟不一致的上游多次更新，不声称常规 OpenAI 响应都会出现这种情况。R15 的正常单次用量、字段缺失、零值和同一事件内非法值回归仍有效。

收口要求：验证最终聚合状态，覆盖跨事件的部分字段、重复更新和输入回退；不合法时返回受控错误或明确标为不完整，不能继续作为完整实报。推理、压缩、存储与统计应遵循一致的缓存子集约束，补充相应回归。
