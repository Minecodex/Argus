## 2. 已闭合的主线，不需要重新询问

- 资源页导航绑定与查询资源范围分开；权限基于 Dashboard、Host、Cluster，不按信号/插件另分权。
- 个人草稿、草稿版本、发布基线、不可变 Revision 与一次确认发布职责明确；草稿保存不反复确认。
- Panel 只有一个有效 builder/DSL 编辑来源；共享变量仅作用于明确引用它的查询。
- 顶部系统条件与 Panel 局部条件分层；局部不能扩大普通查询的顶部资源范围。
- 候选明确消失时回退 All，All 保留对象权限、来源与上层约束。
- 普通查看与 Chat 使用已发布配置；AI 在 Chat 按自己的明确上下文查询，不获取浏览器状态。
- 文件交付属于 AI 工具内部行为，Dashboard 无导出功能；保留显式 limit、聚合和字段选择。
- Q31 的授权 B/C 展开、Q32 的常用 APM 首期范围、Profiling 与原生 Receiver 的后续阶段继续有效。

## 4. 可以直接补齐的工程契约

### E-01 来源身份与混批

当前 [Ingest](../../internal/telemetry/ingest.go) 每个请求/消息只有一套 TrustedIdentity，不同 downstream Collector 混批会拒绝；[Writer](../../internal/telemetry/writer.go) 的 metricSeriesID 不含来源，Trace 派生表也缺来源维度。来源清除/重建边界不能靠随便加属性绕过。

需冻结逻辑来源、采集实例、配置版本、转换版本的身份协议，在混批前分组，或逐 Resource 组验证并拆分消息；落库、去重、派生、查询使用同一来源身份。验收同 ID 不同来源、跨 Host、配置更新后旧批到达等情况，不能仅增加前端厂商标签。

### E-02 Trace/APM 派生与授权

[writeTraceDerived](../../internal/telemetry/writer.go) 仍按当前批次生成摘要，无 root 取首 Span、父服务只查本批、depth 固定。需实现稳定去重、跨批次组装、迟到更新、parent/link、缺失状态和带来源的派生版本。

[Trace resolver](../../internal/telemetry/queryengine/skywalking/resolver.go) 第 262 行起的实例/tag 子查询没有与外层一致的资源限制。只授权 A、未授权 B 时，B 独有属性仍可能影响 A 的 Trace 是否命中；这是当前源码问题，不应等 Dashboard 完成后才处理。所有子查询与关联读取先约束资源/来源，再关联或聚合；拓扑与 RED 派生保留可按对象范围计算的维度。本轮为源码确认，未做线上访问测试。

### E-03 查询结果形状与过滤位置

[KQL](../../internal/telemetry/queryengine/kql/kql.go) 当前收集 parser/stats/order/limit 后生成 SQL；阶段顺序未表达通用逐阶段执行。limit 100 后写 stats 的语句，不能让用户误以为一定先取 100 行再统计。合法顺序和 limit 作用点须明确，不支持的顺序拒绝。

日志聚合仍返回 log_entries，[OpenAPI](../../api/openapi/components/m7.yaml) 未覆盖完整聚合表/时间序列形状。需要结果类型、单位、时间桶、空桶和截断契约，供图型、预览和文件序列化共用。11 种图型不代表任意结果都能互转。

局部过滤绑定须声明语言、目标节点/字段及作用阶段。例如聚合后的结果可能已没有 service，不能只在结果表筛服务，也不能对复杂比率表达式任意修改所有 selector。发布时验证可无损绑定，否则不提供该筛选。Trace 的 root service、Span service、服务目录须明确标识。

### E-04 候选失效的确定性

Q22/Q36 的 All 规则保持，但“没有出现在已加载的候选页”不等于“已经消失”。目录分页、超时、partial、预算截断不能触发误回退。

目录需返回查询状态、截断/游标和当前选值成员验证结果。只有完整结果或精确成员验证明确否定时才回退，其余保留选值并显示验证未完成。这是落实已有决策，无需询问是否允许静默扩大条件。

### E-05 缓存、上下文、来源清单

主设计已增加 Panel 来源和局部过滤，但 §4.4 缓存清单、§4.5 provenance、§5.2 get 与 §5.4 请求示例未全部同步。应统一加入来源绑定/能力版本、本次实际来源集合、按 Dashboard/Revision/Panel 区分的规范化局部参数、全局条件及最终生效条件。查询定义哈希不能代替运行参数指纹，否则 ERROR/All 或同 Host 新增来源可能错误复用缓存/文件。

### E-06 完整导出与 Workspace 状态机

Trace OFFSET 分页和嵌套 LIMIT 不能直接证明完整导出；迟到插入、TTL 删除、替换合并和嵌套截断均需处理。先确定读取边界/结果物化方案、稳定唯一排序与嵌套 continuation；PromQL 分片保留原区间、网格和 @ start()/end() 上下文。

[Workspace access](../../internal/workspace/service.go) 第 148 行起使用独占 lease，单次访问上限 8 分钟；[ImportResult](../../internal/workspace/import.go) 会先完整读取现有 Tool Result。多 Panel 查询可以并行，但写入/读取/分析需按 lease/fence 协调，并补分片提交、原子写入、恢复对账和合法来源登记，不能将任意 export_id 当作 result_ref。

[Workspace 来源检查](../../internal/workspace/source_authorization.go) 是整体依赖校验，某来源撤权可能阻止整个会话 Workspace 继续访问。计划已决定复用 PlanV5，应如实提示并验收；以后若改为按目录局部撤权，需要另行设计。

### E-07 发布并发与生命周期

草稿含 name/description/folder，Dashboard 还含 lifecycle；仅比较 active_revision_id 不足以覆盖不推进 Revision 的元数据变更。Commit 同事务校验元数据/生命周期版本、仍 active、Folder 可用及来源契约有效。现有 PendingAction 的 ExpectedResourceVersion/revalidate 可复用，不能让归档前旧预览覆盖新状态。

## 5. 产品回答与剩余待决项

### Q37 来源绑定的动态性和历史

Panel 选 SkyWalking 后，是在顶部授权资源内动态匹配该类来源，还是固定本次选择的来源实例？新主机加入、停采和重装如何影响已发布图？

已确认：来源类型与顶部授权资源范围动态匹配，具体实例作为局部筛选；停采保留历史，重装区分新旧来源。实现时每次执行冻结实际范围，动态纳入不改变已生成文件的来源事实。

### Q38 顶部跨来源变量

SkyWalking 与 Jaeger 都有 payment 服务时，顶部服务下拉是否自动合并它们？

已确认：不按名称自动合并。环境等统一业务条件可共享，服务/实例默认留在各图；跨来源共享由作者明确映射。

### Q39 明细与下钻的配置闭环

规则要求 AI 只取已发布明细，但人工编辑和 Demo 没有明确的明细查询配置闭环。点击 Trace、关联日志或 AI 进一步分析，需要由谁生成这些定义？

已确认：平台根据来源和图型生成标准下钻查询，随 Panel 一起预览发布，需要时再编辑；人工与 AI 复用，不增加导出配置。日志/Trace 等跨信号关联必须显式记录目标来源、信号、查询和参数映射，不能误要求所有下钻都继承展示信号。

### Q40 Chat 追问跨发布版本

R1 的 Panel P 为 SkyWalking，R2 将 P 改成 Jaeger，用户追问“再看最近十分钟”，采用哪个版本，旧局部条件怎么处理？

已确认：新取数用当时最新 active Revision，单次执行继续冻结版本；解释旧结论用旧证据。来源和参数契约兼容才继承，语义变化明确告知并重选/澄清，不能仅因字段同名照搬，也不能把来源变更当作普通候选失效。

用户已明确选择最新发布版。既有文件不随新版本重写；每张 Dashboard 独立使用其最新默认配置与兼容的明确覆盖条件，不自动扩大范围或将旧文件说成新取数结果。

### Q41 首期 APM 的页面承载

Q32 的服务/实例/接口总览、RED、拓扑、慢错误 Trace 等，是 Dashboard 的专用统计图和下钻详情，还是新增独立 APM 页面？

已确认：采用专用统计图＋展开详情/全屏视图，按厂商分别组织，保持现有 Dashboard 闭环；AI 仍在 Chat。应补类型、查询及验收矩阵，不能用 Trace 列表/瀑布代替整个 APM 清单。

### Q42 归档与草稿

Folder 内还有 Dashboard 时如何归档？Dashboard 归档或编辑者被撤权后，个人草稿如何处理？

已确认：非空分组先迁出内容再归档；保留历史和草稿，归档/撤权期间禁止发布，恢复后重新校验基线。不级联归档，也不静默丢弃草稿。

Q34 已确认展示已接收样本统计，不推算全量；后续插件范围中的“fotelp”名称仍待回答，不重复编号为新问题。容量、延迟 SLO、厂商逐项支持矩阵需在结构明确后细化；本轮没有给出未经测量的规模承诺。

## 6. 实施顺序建议

Task 01 的 T1.0 已承载来源体系、KQL 增强和完整 APM，不能再当作轻量“核实能力”步骤估算。建议按依赖拆分：

1. 冻结来源、变量/局部参数、明细能力和结果类型契约，修复已确认的原型错误。
2. 完成来源身份、授权子查询、存储/去重、跨批次 Trace 组装及查询语义，以真实数据验证负例。
3. 完成单来源真实 Dashboard 的编辑、发布、查询、局部过滤、下钻，再覆盖多来源组合与动态变更。
4. 交付 Q32 的 APM 图型/详情和完整性状态；原生厂商 Receiver 按 Q33 后续阶段接入并分别验证。
5. 接入 Chat 的逐 Dashboard 上下文、完整结果交付和 Workspace 协调，最后做临时 Kubernetes Namespace E2E。

每阶段以真实输入、查询结果、对象范围及可观察交互为退出证据；组件、静态图形或接口命名不能代替功能完成。
