# 模型记录事务、定向验证与探测取证

2026-10-23。R66 完整轮次的 Workspace 查询、实际文件和模型分析结论均完成，但一次模型调用的用量记录不完整，整体门禁拒绝通过。

## 实际原因

同一运行的首次任务在 UTC 17:32:10.110 创建模型调用记录，17:32:10.119 的 PostgreSQL 日志显示 `MarkModelDispatched` 发生 SQLSTATE 40001。该调用的 `dispatched_at` 为空，Worker Pod 没有重启；任务第二次尝试将遗留记录标为 `worker_interrupted`。这次失败发生在提供方请求发送之前，不能当作提供方已经返回完整用量，也不回填或改写历史失败证据。

证据位于 `artifacts/plan8-calico-completion-20261022-r66/workspace-*`，包括调用、任务、Worker 状态、未发送记录与经过脱敏的数据库冲突语句。

## 修正的事务边界

发送登记、模型用量结果与步骤完成记录只修改已拥有的 `model_calls`、`run_steps` 和私有来源记录。统一通过短 `READ COMMITTED` 事务持有当前任务行锁，再执行这些写入；数据库行锁、任务 owner、fence、有效租约与原子提交继续生效。

此事务不包含提供方网络请求、工具执行或业务回调，也不自动重试它们。预算预留、业务确认等其他事务继续使用原有隔离策略。推理与 compaction 共用用量结果持久化方法，避免两个入口采取不同策略。未知、缺失和已知的零用量仍按原有来源语义保存。

真实 PostgreSQL 回归通过实际行锁等待复现旧实现的三个 40001：发送登记、保存已知提供方用量、完成步骤。候选实现连续三轮通过；旧 Worker 的三个写入路径仍被拒绝，私有来源哈希保持一致。包含 compaction 用量来源场景的 Agent 包回归通过。原始失败与候选通过日志分别保留为 `plan8-model-record-red.log`、`plan8-model-record-candidate.log`、`plan8-model-record-agent-regression.log`。

## 验收改进

- 全量组件增加 `model-record-concurrency` 真实数据库分组，共 86 组。
- `--plan8-phase workspace` 使用正式主机、Collector、实际指标和仪表盘前件，只运行选定的模型 Workspace 场景，结果明确标记为局部验收。它不能替代完整部署轮次。
- R66 的 ICMP 默认视图缺样本未在局部探测轮次复现。局部轮次实际观察到零丢包、正常权限和运行中的目标，五类探测及 20 项安装验证全部通过，原失败记录仍保留。
- 正向 ICMP 视图验收先要求实际零丢包样本；全丢包和恢复已有独立负向验证。保持原有时间上限，保留超时前的指标与面板响应，不删除全丢包时隐藏零 RTT 的产品保护。
