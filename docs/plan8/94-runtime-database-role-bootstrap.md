# 分离数据库账号的权限初始化

2026-10-23。R69 的发布演练在旧版基线启动时失败；原部署恢复通过，没有发布或更改原业务数据。

## 实际发现

旧版隔离基线使用 `local-hardening` 的分离数据库账号。Ingest 与 Query 进程启动时均返回 `pki_trust_bundles` 的 `42501 permission denied`，Helm 等待失败并回滚该平台 release。R69 在 `evaluation` 模式下的完整业务 21 阶段、八场模型、门户 12 项和部署健康 20 项已经通过；两种配置不能混为同一项验收。

当前遥测启动代码同样需要读取信任包、确认投影版本和校验证书身份。已有迁移中的角色授权不完整，而且仅在角色当时存在时执行：后创建账号后再运行已经完成的迁移不会补齐。真实 PostgreSQL 回归进一步复现了 Writer 的租户读取和查询审计写入失败。证据见 `artifacts/plan8-runtime-roles-red.log`；其中测试使用真实角色执行领域操作，不使用数据库管理员连接冒充受限角色。

## 职责与实现

运行账号权限收敛到 `internal/storage/postgres/runtime_roles.go` 的共享幂等目录，迁移入口与安装器共用。目录按实际 schema 选择已存在版本的对象，缺少本应存在的表或列即失败；不创建账号，不改密码、成员关系，不授予超级用户、建库或建角色权限。账号在迁移后创建的情况也通过再次执行 `argus-migrate up` 收敛。

原有四类业务/控制服务保持既定的共享业务数据库边界。三个遥测账号单独列明权限：

- Ingest 可以读取采集身份、配置及应用来源，登记和轮换 Collector 证书、消费接入令牌、自动发现服务，并更新限定的观测字段；不能修改采集期望配置、接入端点启停或信任根。
- Writer 读取租户及存储就绪状态，记录保留策略、用量和死信；不读取平台密钥。
- Query 读取租户和调用方证书，登记当前进程的信任包确认，维护查询审计链。审计插入语句带 `RETURNING *`，因此需要读取权限；更新、删除审计事件仍禁止。

遥测启动改为有界、只读地等待控制面创建信任包。权限错误立即失败，不重试成成功；遥测进程不再调用可能创建初始信任根的入口。

## 安装顺序调整

仅平台 Chart 使用“提交资源后由安装器执行就绪检查”的路径：等待数据库迁移 Job 完成，收敛同一权限目录，再执行签发探针、运行组件重启和所有平台/遥测就绪检查。补充检查 PKI Controller 的 Deployment。其他 Chart 继续使用原 Helm 就绪等待。

原因是旧版迁移镜像不包含当前权限目录，若 Helm 先等待依赖该权限的 Pod 就绪，安装器无法进入补齐步骤。该顺序也服务于旧版镜像的真实升级/回退演练。没有删除 TLS 校验、跳过服务就绪或将失败基线标记为通过。数据库 schema 仍为 49；这是基础设施账号权限初始化，不增加业务数据表。

## Helm 4 安装等待修正

R71 完整业务链路通过后，旧版分权基线安装仍失败。实际数据库显示遥测账号对 `pki_trust_bundles` 连读取权限也没有，安装器的权限初始化尚未执行。已核对锁定的 Helm 4.1.0 实现：`RollbackOnFailure` 会把 `HookOnlyStrategy` 强制改成等待全部资源，导致前述显式迁移和赋权步骤仍无法到达。不是缺少信任表写锁权限，不增加信任表写权限。

平台的前置提交因此关闭 Helm 的自动回滚选项，由安装器继续执行迁移完成、权限初始化、签发检查和全部运行服务就绪核验。后续失败记录失败状态并保留资源供诊断或显式恢复；已经迁移的数据不能通过自动切回旧二进制恢复。普通 Chart 的等待和失败回滚保持开启。

新增 `TestLiveHelmBootstrapApplySeparatesRuntimeReadiness`：在自有临时 Namespace 中运行真实 Helm、成功迁移 Job 和等待外部前件的 Pod，确认提交返回后才能补齐前件并使 Pod 就绪；同时验证普通安装仍等待并在失败时删除其运行资源。旧行为已在实际集群复现超时及自动回滚，记录于 `artifacts/plan8-helm-bootstrap-order-red-v2.log`。新增 `installer-bootstrap` 具名检查后，全量注册为 89 组。R71 的 75/76 和完整业务通过记录保持原源码与时间；新冻结版本须重新核验，不把旧演练失败豁免为通过。

候选在 Kind 与 Minikube 的真实回归均通过，临时 Namespace 已按 UID 与所有权清理，分别见 `artifacts/plan8-helm-bootstrap-order-green.log` 和 `artifacts/plan8-helm-bootstrap-minikube-green.log`。后者使用本轮正式组件验收的集群及已缓存的 BusyBox 1.36 前件。两个相关 Go 包回归也已通过；初次注册数量断言仍为 88 的失败和更新后的复验分开保留。


## 多文件 Kubernetes 配置

R72 全量检查在合并的 `KUBECONFIG` 环境暴露 Helm 4 把路径列表当作单个文件的问题；首次状态读取失败后，惰性客户端还可能触发空指针。两个单文件集群的先行回归不覆盖该场景，原失败保持原结论。

安装器只对多文件搜索列表清空 Helm 的单文件覆盖，让 client-go 按标准环境规则合并，并保持显式指定的 context。创建 Helm 客户端前先解析配置，使不存在的配置或 context 返回错误；不修改进程的配置列表、身份或 TLS 策略。新增合并上下文与无效配置回归，并在真实合并环境验证迁移交接及普通失败回滚。证据分别为 `artifacts/plan8-helm-merged-config-red.log`、`plan8-helm-merged-config-green.log` 和 `plan8-helm-merged-config-live-green.log`。
