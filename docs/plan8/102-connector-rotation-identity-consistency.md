# Connector 轮换身份与后续修复的一致性

2026-10-25。当前实施和验收状态见 `progress.json` 与 [交付记录](./57-completion-delivery.md)。

## 实际发现

R81 的组件、完整业务、模型、门户和发布恢复演练通过，原目标也实际完成 Schema 19 → 49 安装。原数据比对通过：13 张业务表、42 个卷、36 个 Workspace 目录，以及 30 张遥测事实表的 1,694,824 行原逻辑记录保留。

原目标 Connector 的正式 PKI 修复拒绝了本地身份。只返回公开 SPKI 摘要的检查确认：两台既有节点的当前私钥与证书相匹配，缓存的公开 CSR 却属于先前私钥。原因是正常证书轮换使用 `saveIdentity` 保存了新私钥和新证书，没有同时更新 CSR。后续 `GenerateLocalIdentity` 正确拒绝了不匹配的材料。

这是实现缺陷，不能列为资源不足或上游限制，也不能跳过 CSR 校验来完成验收。R81 的通过记录保留其原始范围，整体交付继续等待修正版本。

## 修正

- 轮换收到证书后，先验证原有的私钥、证书、URI 身份、客户端用途和信任链。
- 使用已验证的新私钥重建同一 Connector ID 的公开 CSR。
- 通过现有 `saveEnrollmentIdentity` 路径写入私钥、匹配的 CSR、证书和公共 Bundle，最后提交身份元数据。
- 后续 enroll／repair 仍严格验证 CSR 签名、URI 和公钥，不增加接受不匹配材料的回退。

API、角色权限、CA 和域名校验不改变。修正集中在已有 Connector 身份和轮换模块，Collector Receiver 与发行包保持原版本。

## 已损坏缓存的处理

原目标先核对固定 Docker 身份、Connector ID 和现有私钥／证书的公开 SPKI，再仅备份失配的公开 CSR。既有私钥、证书、主机和 Connector ID 保留；正式修复通过已存在的“缺失 CSR 从持久私钥重建”路径完成。两个原节点的正式修复和四个主进程／辅助进程摘要核对通过。公开 CSR 备份和失败记录保留，不把修复动作视为新版本软件验收。

原环境的 Docker 地址绑定也已按实际网络恢复。固定拨号地址只影响 TCP 传输，TLS 继续使用原平台域名。Windows 文本传输曾改变 Linux 修复脚本换行，实际无敏感探针复现后改为原始字节传输。上述执行与环境问题均与源码缺陷分别记录。

## 回归和重新验收

`TestCertificateRotationPersistsIdentityUsableForSubsequentRepair` 使用真实签名的证书、两代私钥和磁盘身份，执行轮换后再次调用正式修复使用的身份生成入口。旧源码实际失败，修正后通过，并验证 Connector ID、轮换后的私钥及完整身份材料保持有效。

该回归加入 `connector-rotation` 强制具名检查，完整注册组增为 90。修正版本需重新冻结源码、制品和相应验收，不将 R81 结果改标为新执行。

后续验收复用保留的双节点 Calico 集群，按顺序隔离执行 drain、控制面指标、同节点采集和 NetworkPolicy 检查，分别保留其实际结果，不宣称使用了两个不同的物理集群。已退出的三个测试数据后端重新建立空数据实例，记录新的容器与挂载基线。原有业务集群、主机和存储继续单独保护。

原目标已在 R81 安装中完成 Schema 19 → 49。后续同 Schema 补丁需保留第一次加密备份、实际安装和原始数据比对，分别记录后续 49 → 49 安装、备份和比对，形成可核对的版本链；不能把后续补丁描述成重新发生的 19 → 49 迁移。
