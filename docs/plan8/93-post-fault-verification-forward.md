# 故障场景后的本地验证转发

2026-10-23。修正开发验收驱动的转发生命周期；不改变平台运行逻辑、证书、权限或生产入口。

## 实际失败与原因

R68 的 87 组组件检查、全量 Go、21 组补充检查、完整部署 21 阶段、八场真实模型和门户 12 项均通过。随后标准部署检查的 19 项通过，`connector-forward-tls` 返回 `connector forward TLS identity: EOF`。原始失败保存在 `artifacts/plan8-calico-completion-20261023-r68/verify/verify.json`，不修改为通过。

`E2EKube.PortForwardService` 会选择一个具体 Pod，并对该 Pod 建立转发。R68 在 08:01:13 切换正式后端后重建了本地转发；之后主机日志故障场景删除 Gateway Pod，验证原采集命令在新连接上只执行一次、控制路径恢复及新主机样本到达。该业务验证于 08:02:52 通过，但末尾健康检查仍使用绑定旧 Pod 的转发。退出清理同时记录了 `lost connection to pod`。

这次失败没有证据表明证书失效，也不能直接忽略为通过。隔离部署按原流程清理，原部署副本、身份与存储恢复核验通过（40.54 秒）。原部署未发布。

## 修正边界

共享 E2E 入口在业务场景结束、调用 `argusctl verify` 之前，调用现有 `refreshPlan6ConnectorForward`：

- 没有本地转发的环境不受影响。
- 核验 Namespace 与 Gateway Deployment 的所有权。
- 关闭旧转发，在相同 loopback 端口重新选择当前 Gateway Pod。
- 原 TLS 主机名、信任根、客户端证书、TLS 1.3 及 HTTP/2 验证全部保留。
- 转发重建失败就停止，不回退不安全连接，也不增加无条件重试。

这是所有 E2E 套件共用的生命周期修正，没有给某项失败测试增加豁免。外部 LoadBalancer 可达性仍与本地转发验收分开记录。

## 验证要求

已有退役 Pod 转发替换测试覆盖旧流关闭、相同端口及拒绝端口变化；已有 TLS 测试覆盖正确身份及无客户端证书、错误身份和不允许的入口。重新冻结后的完整流程需再次经过真实 Gateway Pod 故障，再通过末尾全部部署检查。升级回退及原部署发布仍是后续独立门禁，不由本说明判为通过。
