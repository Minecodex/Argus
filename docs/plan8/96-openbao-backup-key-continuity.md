# OpenBao 备份的解封材料连续性

2026-10-24。Docker 恢复后，对固定版本 OpenBao 2.3.2 的两个独立节点执行真实诊断：源节点创建数据并生成 Raft 快照，目标节点独立初始化后强制恢复该快照并重启。目标原有解封密钥被拒绝，源快照对应的解封密钥成功，原数据可读取。原业务实例未参与诊断，临时容器及卷按标签和固定 ID 清理。证据：`artifacts/plan8-r74-openbao-restore-key-probe-recovery4.json`。

## 实现边界

此前 M8 备份包含快照与应用 Token，缺少保存在卷内的 `argus-bootstrap.json`。恢复到独立初始化的目标后，原解封 sidecar 仍读取目标旧密钥，无法解封源快照。这属于本地恢复流程缺项，需要在发布门禁之前修复。

备份清单升级为格式 2：源解封材料与快照一起进入既有加密归档。采集前后检查源材料一致；只接受 local-hardening 当前的一份 Shamir share、阈值 1 以及有效根 Token，不扩大为外部托管密钥或多份额恢复支持。原始 JSON 格式保留，以兼容既有 bootstrap Job 与 sidecar 的文件读取方式。密钥不进入日志、命令参数或模型。

解密后先校验版本、清单文件摘要和必需解封材料，再创建独立恢复环境。格式 1 因缺少必要恢复材料而明确拒绝，不伪称可完整恢复。目标使用自身当前根 Token 恢复快照，随后经主容器的可写卷、标准输入和同目录原子替换安装源材料，再重启并验证。解封 sidecar 保持只读挂载；本地暂存与目标文件权限均为私有。写入或后续验证失败返回失败，不报告恢复完成。

## 验证

新增独立真实双节点回归，复用产品快照、恢复、原子写入及加密归档代码：目标旧密钥拒绝、源材料加密往返、UID 1000 写入、文件权限 0600、实际重启、按 sidecar 读取方式解封，以及原 transit 密钥对原密文解密。加入既有 `postgres-backup-restore` 组，与 PostgreSQL 恢复和 Windows 跨盘文件传输一起运行；完整驱动仍为 89 组。

先行真实双节点回归已通过，耗时 24.92 秒；实际完成重启后原 transit 密文解密以及归属校验后的容器、卷清理，见 `artifacts/plan8-r75-openbao-live.log`。此外覆盖缺失、格式不支持、材料无效、摘要变化和不安全组件名称的提前拒绝；CLI 与验收驱动两个 Go 包回归均通过。

局部验证不能替代独立完整发布演练、原环境保护及最终发布验收。当前结果见[交付记录](./57-completion-delivery.md)。
