# Collector 断线后的结果核验

状态：实现及真实 PostgreSQL、Connector 客户端回归通过；r28 正式故障已触发并验证 unknown，完整补报仍待重跑。它不代表整体 Plan8 完成。

## 已复现的问题

r27 已实际读取应用文件日志，验证轮转与重启后的 checkpoint。最后停用规则时，Collector 已执行配置重启，但控制连接在回报前中断。原命令变为 `result_unknown/CONNECTOR_DISCONNECTED`，新连接已经在线，采集实例却仍显示期望版本 4、生效版本 3、pending。证据在 `artifacts/plan8-completion-deployed-r27/plan8-service-apply-481d7dc9-6997-547d-9d73-c7b770e53fd1.json` 与对应 readiness、主机 journal 中。

源头有四处：命令断线状态未投影到 Collector/采集实例；以新连接代次查找旧命令导致补报查不到；原有结果摘要缺少完整证明；普通命令完成后的结果只在会话循环中保存，断线可能先结束该循环。

## 实现

复用现有 `CommandResult` 类型化结果与本地私密 journal，不新增业务写指令。仅允许回传请求中明确指定的 Collector 管理结果；其他本地结果、损坏记录、过期连接代次均不进入此路径。已经批准的 Collector 操作采用进程生命周期和既有三分钟执行上限，控制连接重建不会取消操作；结果先保存，再通知会话。

Gateway 只允许当前有效连接核验同企业、同 Connector 的旧未确认命令，检查结果类型、Schema、完整字节摘要、Collector ID、配置版本和配置哈希；更新原命令与应用生效状态处于同一事务。重复证明使用 protobuf 语义相等判断，避免 PostgreSQL JSONB 的键序和空格规范化导致误拒绝。旧证明不能覆盖更新的配置意图。

断线时立即投影 unknown；新连接建立也会原子补齐旧 Gateway 未能记录的未确认状态。当前连接每 15 秒检查至多 64 个待核验 Collector 命令，支持操作晚于重连完成的情况。该过程只交换证明，不能重新执行安装、更新或卸载。原有普通命令代次约束继续保留，新路径单独核验当前连接与旧命令归属。

## 已有验证与下一步

`artifacts/plan8-collector-reconciliation-regression.log` 的两个包回归通过。新增真实隔离 PostgreSQL 场景包括断线投影、旧清理丢失、新连接核验、拒绝旧连接/跨企业/损坏或伪造结果、摘要不能冒充完整证明、投影失败回滚、重复补报无副作用，以及更新意图不被覆盖。客户端另验证私密 journal 的白名单补报、命令选择边界和会话已结束时仍保存完成结果。

正式驱动现为最终文件规则停用加入实际故障：只在本轮拥有的 Linux 容器添加短暂服务启动延迟和启动计数，再在原命令已确认后按 UID 删除临时 Namespace 的 Gateway Pod。验收要求新连接补报原命令、生效停采、同配置只有一条写命令且实际 Collector 仅启动一次。临时 drop-in 与计数文件在阶段结束清理；原环境和临时 Namespace 仍执行统一恢复检查。Journald 和后续阶段尚未因此计为通过。

r28 已实际触发上述故障并正确投影 unknown；驱动误将预期中间态作为失败，尚未完成核验就清理。因此不计整体通过。现为该故障场景在原三分钟窗口等待可信补报，所有最终条件保持；普通服务等待仍对 unknown 立即报告。下一轮同时使用正式 `0.3.2-plan8`，完整结果仍待运行。
