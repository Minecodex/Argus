# Compose 运行包与环境约束

## 分层组成

| 层 | 承担内容 | 实际运行位置 |
| --- | --- | --- |
| 正式 Argus | 门户、API、Worker、遥测、存储、Workspace 等 | 现有部署，部署前重新核验 |
| 本批测试基础设施 | Linux 主机、数据库/中间件、测试业务服务、流量客户端 | 本批独立 Docker Compose 项目/网络/卷 |
| 补充目标 | Kubernetes 集群、Windows VM、真实 ARM 主机 | 独立创建/接入脚本，不能声称普通 Compose 已覆盖 |
| 接入和配置 | Host/Cluster/Collector、应用、凭据、仪表盘、告警、授权 | 门户或正式 API/Tool |
| 负载与观察 | 实际请求、数据读写、故障/恢复、E2E、页面交付 | 本批客户端与真实门户 |

Compose 只负责服务进程和依赖的运行；`docker compose up` 成功不代表监控接入、告警或界面已经验收。

## 每批文件交付约定

以下是后续落实时的目录约定，**不是当前已存在的文件清单**。一个子批次应能独立部署，不依赖其他批次的存活环境。

```text
docs/plan9/
  batches/B01-linux-host.md           # 场景说明
  runtime/B01/
    compose.yaml                     # 具体服务、网络、卷、健康与资源限制
    .env.example                     # 非敏感参数名，无可用密码/Token
    images.lock.json                 # 实际验证的镜像标签、摘要、架构和来源
    config/                          # 服务配置、原生 Collector 所需输入
    workloads/                       # 请求、协议操作和应用埋点代码
    scripts/                         # prepare/up/enroll/load/fault/recover/verify/down
    runbook.md                       # 当前真正可用的命令与参数
  runtime/B09/                        # Compose 辅助服务 + 集群创建/清单
  runtime/E01/                        # Windows VM 前件/接入/清理，无伪 Compose 替代
artifacts/plan9/<run-id>/
  run.json                           # 状态、版本、权限主体、预算、时间
  resource-map.json                  # 实际资源 ID/依赖/所有权/借用关系
  timeline.jsonl                     # 负载、故障、恢复和操作事件
  checks.json                        # 实际自检结果与未通过项
  handoff.md                         # 用户查看入口与时间窗口
  review.md                          # 用户反馈、修复、复验、用户通过
  cleanup.json                       # 清理对象、残留、原环境健康
  screenshots/                       # 实际门户截图
  private/                           # 本机受限凭据；不提交，完成后按需撤销/清除
```

可以在 `runtime/common/` 复用已验证的主机镜像构建、负载小工具和配置 API 客户端，避免复制维护；各批 runbook 必须显式列出依赖。运行脚本可用 PowerShell 调度、容器内 shell/应用客户端执行，不再搭建一个平行测试平台。

## Compose 必须具有的内容

- 明确且唯一的 project name；不硬编码会跨批冲突的 `container_name`。所有服务、命名卷和网络带本批 run ID 与所有权标签，例如 `io.argus.plan9.run`；标签命名空间不等同产品资源标签。
- 平台对象使用允许的自定义标签，例如 `plan9_run`、`plan9_batch`，不写保留的 `argus.io/*`；平台对象不支持标签时使用名称前缀加准确 ID 清单。
- 镜像固定已核验版本和摘要，包含架构；不使用 `latest`。优先复用当前源码/Plan8 已验证组合，但历史缓存和可下载性必须重新验证。
- 健康检查验证实际进程/协议就绪；数据库和应用初始化只在本批目标执行。重跑必须检查已有身份/资源，不无条件重新生成密钥或清数据卷。
- 每个服务和负载明确 CPU、内存、PID、日志轮转和数据量上限；负载参数写进 run 记录。健康等待/安装/查询/故障均有超时和恢复步骤。
- 凭据通过受限文件/Secret 输入，避免命令行、日志或 `docker compose config` 输出泄漏。渲染检查只输出脱敏结果；不得复制历史 E2E 镜像里的固定账号密码作为本批登录。
- 只有必要端口发布到明确地址；默认不向整个局域网开放。Windows 浏览器入口、Docker 内地址、Kubernetes 中可达地址分别记录；`127.0.0.1` 不跨容器/Pod共享。
- 没有宿主 Docker Socket 和无关磁盘挂载；需要系统权限的 Linux 主机/cgroup 场景单列实际权限及挂载。优先使用专用 VM，或经过验证的隔离 systemd 容器，不挂载可写的宿主服务目录/cgroup 树。
- 故障只影响本批目标，网络规则限定本批网络/身份并有恢复方法；不得通过断开正式平台网络、耗尽宿主磁盘或改全局 DNS 产生异常。

Linux 主机基础镜像可以参考现有 `deploy/docker/e2e-systemd-host.Dockerfile` 的 systemd 条件，但不能直接把其中 E2E 遥测生成器、固定测试密码及历史状态当作本计划的数据链路。正式 Connector/Collector 使用当前发行物及正常安装流程。

## 真实性要求

| 允许 | 不允许作为本次真实验收证据 |
| --- | --- |
| 客户端实际向本批数据库写测试业务数据 | 直接向 Argus PostgreSQL/ClickHouse 写资源、指标或告警 |
| HTTP 请求触发应用逻辑，真实 SDK 记录 Span/日志 | 预写 OTLP/Span JSON、回放历史遥测冒充本次调用 |
| 操作系统真正运行负载/服务并由原生 Receiver 采集 | 固定曲线、随机指标、mock receiver、直接改健康状态 |
| 模型配置测试及真实 Provider 会话/工具调用 | 回放模型、固定答复、预置工具结果冒充真实分析 |
| 真实 SSH/RDP/终端、录像和审计 | 模拟终端输出、仅创建会话记录 |
| 只读核对业务状态/数据（必要时） | 直接改表绕过身份、预览确认、安装、注册或权限 |

造测试业务负载是本计划目的；证明的是服务真的执行过这些操作，以及 Argus 正常采集和展示结果。人为设置的小阈值或短窗口应标记为测试策略，不能包装成生产告警建议。

## 资源预算与保持策略

以下为初始规划上限建议，不是已测容量或性能承诺。每批先依据 Docker 分配资源、主环境占用和目标镜像最低要求确定实际预算。

| 类型 | 同时运行范围 | 初始建议 |
| --- | --- | --- |
| 轻型 B01/B02/B04/B08/B11 | 一个子批、1～3 个测试主机/目标 | 约 2～4 vCPU、2～4 GiB 内存，有限测试数据 |
| 数据库/应用 B03/B05/B07/B12/B13 | 一组必要依赖 | 约 4～6 vCPU、4～8 GiB；消息/索引/行数硬上限 |
| 重型 B06 | 一次一种重型数据库/搜索服务 | 按镜像最低要求预检，预留约 4～8 GiB；不足则拆分或等待 |
| Kubernetes B09/B10 | 一个独立测试集群，节点数依操作需求决定 | 预留约 6～12 GiB；资源不足不与其他批次并行 |

vCPU 是计划并发预算，不代表必须独占；安全上限以运行前实际核验为准。资源不够时先减并发、缩数据量、拆子批；本计划的人工查看依赖正式门户/采集/评估，默认不停止这些服务。确需调整现有部署时单列影响，不能把全部停机当默认准备步骤。

负载默认有时限，测试数据有容量上限；达到上限后保持主机/服务和页面可查看，结束增长性负载。展示需长时间持续时用低频、限量、可轮转的真实业务请求维持；持续大 CPU/内存/磁盘压力不可作为等待用户的方式。

## 网络、模型和通知

每批记录执行端→目标、Connector→平台、Collector→遥测、Worker→模型、通知发送端→测试接收端的真实路径和 TLS/鉴权。堡垒机场景还要证明成员不能直接绕过中继；必要隔离由专属测试环境提供，不更改正式环境的全局规则。

真实模型只使用已授权配置或用户提供的新配置，密钥不进入 Compose/Markdown/截图。模型的可用性、预算与调用结果现场核验，不根据历史 `glm-5.3` 成功记录宣称现在可用。

默认只建立站内告警和本批测试接收端。外部消息、邮件和群机器人真实发送需要明确的目标授权；本计划不自动向正式通知渠道发测试告警。
