# 每批执行、交付和销毁流程

## 1. 指定批次与前置检查

收到“部署 Bxx”后记录用户指令和新 run ID。运行命名建议为 `p9-b01-20261026-01`；重试同次运行复用记录，完整重建分配新 ID。

在任何部署前核对：

- 当前正式部署版本、API real 模式、门户登录和所需权限、服务健康、时间同步；只读记录原业务资源基线。
- 当前 Docker/Kubernetes context、剩余内存/CPU/磁盘、占用端口、现有网络及卷。主环境必要服务必须有资源余量，不能因测试负载让门户不可用。
- 当前版本的组件/采集能力、真实镜像摘要、认证/拓扑组合、已有默认模板；旧测试镜像已清理时重新构建，不能假定缓存仍存在。
- 从实际 Collector/Connector 所在网络验证 DNS、平台 HTTPS/Gateway/遥测入口、CA/SNI、回连和被监控端点；不关闭证书验证。
- 平台凭据、测试主机 Host Key、模型/通知/VM 等本批必要前件。只引用受保护材料，不将原值写进报告。

按“已验证、未验证、缺少前件、不适用”列出结果。只阻止依赖缺失前件的执行，不重跑与当前场景无关的全套验收。前件缺失的批次不能标为可供完整验收。

## 2. 准备本批运行包

按 [环境规范](./03-environment-and-compose.md)生成本批 Compose、配置、负载/故障/恢复脚本，以及 Kubernetes/VM 的适用补充文件。

先验证渲染、配置、依赖、版本、端口、资源上限和清理归属；记录源码状态及本批文件摘要。当前工作区可能有未提交开发内容，不能只记 HEAD 就声称绑定了全部源码，也不覆盖其他改动。

脚本区分准备、启动、接入、造负载、故障、恢复、自检、交付和清理。执行失败停止后续依赖步骤；未知结果先查实际状态，不盲目重试创建资源或重复消费一次性确认。

## 3. 启动真实环境与平台接入

1. 启动本批网络、主机、服务和健康检查；等待进程与业务协议就绪。
2. 通过正式安装/注册流程接入 Host/Bastion/Cluster；记录资源 ID、身份、路由、安装与预检结果。
3. 创建测试监控账号和平台凭据引用；通过正常配置流程安装 Collector、创建采集实例/规则/应用接入。
4. 等待配置生效并取得**当前运行的新鲜样本**。分别检查在线状态、desired/effective revision、来源身份、采样时间和实际查询，不能用其中一项代替其他项。
5. 创建/绑定适用仪表盘和需要的副本，建立专属告警后台身份/资源权限/策略。通知仅配置本批允许的接收目标。
6. 生成 `resource-map.json`，以真实 ID 连接容器/服务→Host/Cluster→采集/来源→应用/仪表盘→告警→会话；列出借用资源和本批新建资源。

所有平台写入经过门户/正式 API/Tool 的领域服务、预览和确认。使用 API 自动化必须遵守当前会话、CSRF、权限和一次性确认约束；不能走测试专用入口、改表或伪造平台对象。

## 4. 产生数据、故障和恢复

按固定时间线执行 baseline→load→fault→recovery，各阶段记录 UTC 原始时间及 `Asia/Shanghai` 展示时间。低负载预热先形成至少两个完整查询窗口；默认目标为 10～15 分钟，按实际采集/告警周期调整。

- 负载必须真实执行且有上限：请求数、并发、消息/行/文件数量、总字节、持续时长和退出条件。
- 每次只注入一类主要故障，保留健康对照；记录故障对象、执行方式、开始/结束、恢复方法与实际结果。
- 在触发告警前固定阈值、窗口和恢复防抖。等待“评估→触发→恢复”的真实状态，不手工创建告警事件。
- 至少复核一个关键指标与目标原生状态/计数，确认单位、Counter/Rate、范围、来源和时间对齐。容器共享内核导致的口径限制写入结果。
- 主动停采、进程故障、采集认证失败、查询失败分别执行/记录；没有数据不得补 0 或判健康。

超出本批预算或主环境健康变差时，停止测试负载并恢复本批故障，保留现场和原因；不能通过停正式数据库/遥测服务让验收继续。

## 5. 自动自检后交付用户查看

先运行与本批相关的真实 E2E：正常接入→取数→仪表盘→告警→适用会话/操作。浏览器连真实门户、使用真实后端；mock 用例可辅助开发，不能作为本批自检证据。

每批交付一份 `handoff.md`，按[检查表](./04-review-and-evidence.md)给出真实页面链接、对象名称、建议查看顺序、应看到的内容、当前状态和故障/恢复绝对时间。深链接来自实际 UI/路由与真实 ID，不预造 URL。

交付前保留：正常低负载、适合持续观察的低风险异常（若本批需要）、已恢复事件及历史窗口。负载上限到期时自动停止负载而不是自动删除环境；清楚说明哪些异常现在还能看、哪些应切到历史时间查看。

只有必需自检项满足且已列清差异才标 `ready_for_review`。存在阻塞时仍可提供部分页面，但状态是 `blocked` 或 `changes_requested`，不能宣称本批全部准备完成。

## 6. 用户查看、修改与复验

用户的问题记录到本批 `review.md`：页面/对象、现象、预期、语言/主题/视口、时间范围、复现条件和证据。

修复遵守仓库架构、共享组件、双语/主题约束；涉及代码或配置改变，更新对应文档和必要回归。保留原失败记录与相同测试对象，能原位复验时不销毁重建掩盖问题。部署新版本后重新验证受影响链路和页面，记录新版本与原数据是否连续。

当问题与本批无关但影响现有业务时单独记录；不得为了让当前图表好看临时硬编码、放大权限或降低验证要求。

用户说“通过”才写 `accepted`，记录对应原话、时间和运行版本。自动 E2E 成功只记录自检通过。

## 7. 用户要求销毁/下一批后清理

顺序固定为“保存证据→停止测试通知和负载→平台收尾→基础设施清理→双向核验”。

1. 封存查看记录、实际样本/配置摘要、告警/会话 ID、截图、失败及修复记录。清理前记录原环境与本批资源实际清单。
2. 停止本批负载和故障定时器，恢复安全状态；通过正式配置停用本批告警策略/路由和采集，关闭本批远程/转发会话，避免销毁产生新的测试告警。
3. 按产品依赖顺序解除本批关联、删除或归档本批仪表盘副本/应用/监控目标；撤销本批密钥/授权/临时身份。受管默认模板定义属于共享产品，不删除。
4. Host/Bastion/Cluster 按既有卸载和退役流程处理。成员先于堡垒机；可达时先验证本机卸载，再删除运行目标。失联时记录残留和强制退役结果，不伪造卸载成功。
5. 用已记录的 Compose 项目/容器 ID、卷/网络标签、Namespace UID/集群所有权清理。禁止全局 prune、按模糊名称删除、删除未列入本批清单的卷或集群对象。
6. 检查本批活跃资源、会话、通知、授权、容器、卷、网络和测试集群/Namespace 无非预期残留；检查正式门户、后台、共享依赖和原数据仍正常。

平台允许保留的审计、告警历史、会话和已采集历史按正常保留策略保留，标清已归档/来源退役。它们不是仍在运行的测试环境；不直接清库去制造“零记录”。要物理清除历史需另列明确对象与受支持流程。

销毁失败记录 `cleanup_failed` 并列出具体残留，先解决残留再运行下一批，避免环境混杂。需要保留的镜像缓存单列；未获清理指令不删除共享镜像/构建缓存。

## 状态约定

```text
planned → preparing → deploying → validating → ready_for_review
                                      ↑              ↓
                                      └─ changes_requested
ready_for_review → accepted → destroying → destroyed
任一执行阶段 → blocked；清理阶段失败 → cleanup_failed
用户明确跳过 → skipped
已部署但自检未全过 → deployed_with_known_issues → 同批修正/复验
```

用户要求销毁未验收批次时也可进入 destroying，但 `review_status` 保留未通过。运行状态和验收结论分开记录；destroyed 不代表 accepted。当前状态登记在 [progress.json](./progress.json)，详细事件追加到各 run，不覆盖历史失败。

`deployed_with_known_issues` 可交付页面供用户查看，明确未通过项；不计为自检全过或人工通过，也不自动进入下一批。当前批次状态以 `progress.json` 为准。
