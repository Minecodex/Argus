## 部署步骤

1. 核验主环境健康、门户 real 模式、登录、资源余量和当前采集能力；准备本批镜像和 Compose，记录摘要、网络、端口、资源与负载上限。
2. 启动两台主机，验证真实 systemd、SSH、独立机器身份；安装目标通过实际执行位置访问 Argus HTTPS/Gateway/遥测路径。目标入口不是平台 Pod 可达的 loopback 时，使用已支持的安装/隧道路径。
3. 经正式连接测试/预览/确认接入两台主机，安装 Collector，打开四类适用自身采集；记录在线状态、配置生效及当前样本。
4. 查询原生 CPU/内存/文件系统/网卡/进程/服务状态，与 Argus 对照。共享内核口径必须写入交付说明。
5. 打开受管主机、进程、systemd、Collector 默认图，验证 A/B 范围；配置专属策略/后台身份，先等待正常评估。
6. 执行下表中的实际变化；自动检查实际图表/告警和四种语言/主题，整理用户查看入口后保留环境。

## 场景时间线

时间为初始计划值，最终依据实际采集周期、数据新鲜度和告警持续窗口确定；每一步都有最大等待，超时记录失败，不能无限等待到“看起来正常”。

| 阶段 | 真实动作 | 应有结果 | 保留方式 |
| --- | --- | --- | --- |
| 正常基线 | 两台主机低负载运行约 10～15 分钟 | 当前样本、正常服务与告警评估、图表至少两个完整窗口 | 继续低负载 |
| 有界负载 | A 的专用进程进行 CPU/内存/文件读写/网络操作，逐种执行 | 对应实际指标变化；单位/速率正确 | 每种最长约 3～5 分钟，自动停止 |
| 服务异常 | 专用服务真实失败并保持已加载单元 | systemd 状态与策略匹配；告警实际触发 | 低资源故障可保留，交付时说明 |
| 故障恢复 | 恢复专用服务，停止负载 | 样本恢复、告警按真实窗口恢复、有历史时间线 | 记录绝对窗口 |
| 单项停采 | 正式停用 A 的一项采集并重新启用 | B 和其他能力不受影响；停采不当健康 0 | 恢复后核验新样本 |
| 全部指标关闭 | 通过正常配置关闭 A 全部固定指标，再恢复 | Connector/Collector 控制在线，指标不继续隐式上报；历史可查 | 最后恢复正常配置 |

独立 CPU/内存不一定能由两个 Docker 主机隔离观测：共享内核指标可能同时反映 A 的负载。因此对照重点同时使用来源身份、专用进程/服务以及实际可隔离指标；如验收要求完整主机级隔离，准备两台 VM 后执行，不把容器共享现象当成功或无依据当缺陷。

磁盘负载只在专用目录/测试卷中创建有限文件；文件系统占用率可能反映共享存储，不以写满宿主磁盘触发告警。网络负载只连接本批端点。

## 仪表盘与告警配置交付表

| 类别 | 配置/检查内容 |
| --- | --- |
| 主机基础 | CPU/内存/文件系统/磁盘 I/O/网络；实际有值、来源与范围准确，缺硬件/GPU/云元数据保持不可用 |
| 进程 | 只显示 Collector 可见进程；专用工作进程的 CPU/内存/I/O 按实际字段展示，不泄漏敏感命令参数 |
| systemd | 专用服务 active/failed/recovery；单元卸载后缺样本不能硬补 stopped=0 |
| Collector | 当前生效配置、接收/发送/失败/队列等已支持自监控；控制在线与数据状态分开 |
| 服务告警 | 基于真实可查询状态定义正常/异常与持续/恢复窗口；若单元指标能力不足先列缺项并修正方案 |
| 负载告警 | 选与实际口径一致且可安全触发的指标；阈值/单位/窗口在施加负载前冻结，明确“Plan9 测试” |
| 停采与数据缺失 | 主动停采的 suspended/not_evaluated 语义；真实失联/无数据按策略分别验证，不伪造恢复 |

默认只产生站内告警实例与历史；通知通道的完整专项放到 B13。告警后台主体必须具有本批资源数据授权，不能靠管理员能看到图就推定评估主体能查询。

## 完成与清理条件

- 自检：两台主机正常接入；关键原生值/来源与查询匹配；适用图表有本次新数据；实际告警触发及恢复；停启隔离与四种界面组合通过。
- 人工：用户检查并明确通过，或列出待修改问题。缺项、失败、共享内核限制独立记录。
- 清理：按[统一流程](../02-execution-workflow.md)停用本批策略/负载/采集，正常卸载/退役本批 Host 与凭据，清理 Compose 专用容器/卷/网络，核验无活跃残留及正式环境健康。告警/审计历史保留。
