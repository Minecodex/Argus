# 用户查看清单与证据

## 每次交付给用户的内容

`handoff.md` 必须简短到能直接开始检查，至少包含下表。实际值部署后填写，不用示例 ID/URL 占位宣称交付完成。

| 信息 | 必填内容 |
| --- | --- |
| 当前批次 | Bxx/子批、run ID、部署版本、准备完成时间 |
| 查看入口 | 主机/应用/中间件/K8s/仪表盘/告警/会话等真实链接和名称 |
| 建议顺序 | 3～8 个步骤，每步一句“看什么、应有什么结果” |
| 当前场景 | 正常、仍保留的安全异常、已恢复的异常分别列出 |
| 历史窗口 | 负载/故障/恢复的绝对起止时间与时区；可直接选择的时间范围 |
| 真实来源 | 目标身份、采集/应用来源、实际操作摘要、数据新鲜度 |
| 自动检查 | 通过项、未通过项、明确不适用项；不混算 |
| 仍在运行 | 容器/集群/负载、预计保持方式、资源上限和已到期的负载 |
| 反馈方式 | 用户直接描述页面问题；无需填写复杂表格 |

页面深链接、固定历史时间范围和名称必须核验可用。用户不应为了找当前批次在大量旧测试资源中逐个筛选。

## 每批共同检查

| 方面 | 用户重点看什么 | 自动检查的证据 |
| --- | --- | --- |
| 资源入口 | 名称/状态/来源一致，当前批次易找到，列表和详情能互相跳转 | 实际对象 ID、创建/安装操作和页面 |
| 数据 | 曲线随真实操作变化，时间/单位/图例正确，区分 0、无数据、不可用 | 目标原生状态/计数、实际查询样本与绝对时间 |
| 范围 | 切 A/B、应用、环境、Namespace 不串数据；显式空选择保持空 | 来源/Scope/查询参数与负向查询 |
| 仪表盘 | 图不重叠/截断，图例和 Tooltip 可读，时间范围、刷新、下钻有效 | 真实数据截图、相关交互 E2E |
| 采集 | 配置/生效版本清楚，停采和采集失败不同，历史仍可查看 | 配置版本、状态、当前样本时间和停启记录 |
| 告警 | 真正触发、分级/原因/阈值清楚，恢复有记录，能跳到目标 | 策略/评估主体、评估/实例/历史/投递 ID |
| 聊天（适用） | 工具、计划、确认、执行、文件和结论可以回看 | 真实 Provider 用量、Run/Tool/Workspace 及文件摘要 |
| 远程（适用） | 真实输出、停靠/缩放、连接/断开、回放和审计一致 | 会话 ID、目标身份、实际命令、录像与事件 |
| 权限 | 无权操作明确拒绝，撤权后旧页面/会话不继续获取内容 | 原主体与受限主体的实际请求/浏览器结果 |
| 生命周期 | 失败可诊断、重试不重复创建，归档后历史语义明确 | 操作状态、版本、重试与清理清单 |

## 桌面视觉范围

每批在真实门户至少覆盖 `zh-CN/light`、`zh-CN/dark`、`en-US/light`、`en-US/dark` 四种组合；固定主视口 1440×900，并对当前批次最密集页面复核 1280 与 1920 宽度。高度和缩放比例写入证据。

重点检查长名称、较多图例、空数据、错误、加载、分页、多列/抽屉/弹窗、工具卡片、终端停靠和禁用状态。对同类页面复用代表性场景，改动后只补测受影响范围，不为每个指标重复跑整站矩阵。

沿用 `@argus/ui`、design tokens、`.argus-*` 和模块 i18n；问题修复不能另建组件/样式体系。移动端不进入本计划验收。

## 每批至少一条完整证据链

```text
本批目标身份 + 实际业务操作 + 时间线
  → 原生采集/应用 SDK + 生效配置/来源
  → Argus 正常摄入 + 带身份/时间的实际查询
  → 仪表盘当前结果 + 实际告警触发/恢复
  → 真实门户操作/截图 + 用户确认
```

具体最小证据包括：

1. 目标版本/镜像摘要、资源和权限主体、实际接入 ID/路由。
2. 实际请求/命令/SQL/消息计数，故障和恢复事件；敏感值脱敏。
3. 至少一个关键指标与原生输出对照，含单位、采样周期、查询窗口、聚合和覆盖说明。
4. Collector 生效配置与新鲜样本、仪表盘 ID/revision/查询来源、告警策略/实例及评估结果。
5. 适用的模型调用、工具记录、文件、终端/录像；平台配置测试成功不等于一次实际业务会话成功。
6. 真实 E2E 的输入环境/版本/结果、截图、用户反馈及复验。
7. 清理前后所有权清单、失败/残留及正式环境健康核对。

读数据库核对可以作为辅助证据，不能替代正常 API 取数和用户页面。图表有数也不能单独证明来源正确。

## 通过和缺项怎么记

- `self_check=passed`：本批必需自动核验通过，仍等待用户查看。
- `review_status=accepted`：用户明确确认该 run/版本通过；截图或模型判断不代替用户意见。
- `blocked`：必要前件或链路缺失，具体写明影响项。其余页面可继续查看，但不算完整通过。
- `not_applicable`：该平台/协议确实不具备能力，写明既有支持边界；不能用于隐藏本应存在但失败的指标。
- `skipped`：用户明确跳过，保留原因，不计通过。
- `runtime_status=destroyed`：本批运行环境已清理；与人工是否通过分开记录。

已知暂缓能力保持单列；某项新发现不支持、某项实现故障和某项缺测试环境分别记录，不能都写成“暂无数据”。

## 问题记录字段

每个问题使用本批稳定编号，例如 `B01-ISSUE-01`，记录页面/对象、发生时间、重现步骤、预期、实际结果、影响、证据、修复版本、自动复验和用户复验。用户只需口述问题，记录整理由执行者完成。

失败证据保留，修复后追加新结果；不得覆盖原失败报告、删失败 Run 或把一次新建成功说成原现场已恢复。
