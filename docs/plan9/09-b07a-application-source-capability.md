# B07a 应用接入与查询修正

2026-11-04，基于用户已经更新的 Plan11 代码和 `local-20261102-plan11-review` 部署继续真实场景。

实际 OTLP HTTP SDK 已自动发现两个服务，指标、日志、APM 服务/实例/接口及跨服务拓扑均可正常查询。但通过正常 API 发布应用仪表盘时，静态验证通过，草稿采样和发布返回 `DASHBOARD_INVALID`。

根因是版本名所属的契约不同：配置生成器将应用 SDK 来源标记为 `application/v1`，仪表盘发现目录声明对应 OTLP/Jaeger 查询能力为 `v1`，来源解析要求两个字符串完全相等。已有基础设施测试使用普通 `v1`，没有覆盖生产 SDK 配置生成器的这个组合。

修正位于共用仪表盘来源解析层，适用于目录候选、草稿采样、发布和执行：仅将已授权的 application 资源、OTLP/Jaeger 来源的 `application/v1` 视为现有 `v1` 查询契约。保留来源原始版本、身份、修订和权限检查；其他类型及未知版本不放开。没有改写样本、历史来源或数据库记录，也没有替换 Collector 发行包、签名和用户的新代码。

回归使用生产 `configbundle.Render` 生成 OTLP/Jaeger 应用来源，再验证消费侧的能力匹配；同时覆盖非 application 资源、非 SDK 来源与未知版本拒绝。正式闭环仍由本批真实 SDK、正常发布、三信号取数和浏览器验证完成，最终结果以 [B07a 查看记录](./batches/B07a-review.md)为准。

连续真实请求还发现应用拓扑页复用了列表的 5,000 行预算。拓扑需要先重建原始 Span 父子关系，再归并为服务节点和依赖边；两个服务的每秒约两次调用即可在十五分钟内超过该预算，即使最终只有两个节点。拓扑页改用引擎已有的 50,000 行默认有界预算，其他视图仍为 5,000 行，扫描字节、超时和返回字节限制保留。未删减真实请求、收窄时间范围、放开授权或把超限结果伪装完整。


## 同次 PromQL 查询重复选择器的读取复用

持续真实验收中，Redis 默认图的最后一个面板偶发超过整板 256 MiB 扫描预算。原始计量显示命中率表达式五次读取命中/未命中序列，单面板约扫描 80 MB。同一查询中相同匹配器与读取提示改为共享已读的不可变序列，每个使用方仍获得独立游标和样本迭代器。

复用仅存在于一次 Querier 内，授权资源/来源快照和时间边界在创建时冻结；匹配器、提示、排序或限额变化不共享，跨请求不共享。保留错误、取消与直方图复制语义，实际扫描按实际发生的读取计量，没有放大配额、修改公式或缩短验收时间。回归执行真实 PromQL 公式，验证命中率仍为 0.8、读取由五次降为两次，并检查等待取消、游标独立、不同查询隔离及选择条件区分。
