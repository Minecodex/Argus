## 配置与业务行为

| 设置 | 请求含义 | 适用范围 |
| --- | --- | --- |
| 供应商默认 | 不发送 `reasoning_effort` 覆盖 | 两种现有协议 |
| 低 / 中 / 高 / 最高 | 发送 `low / medium / high / max` | 当前 Chat Completions 路径，具体模型须兼容性测试 |

模型列表显示已保存档位；创建与编辑共用表单、共享 Select/Field、双语文案和现有配色。Responses 的显式档位暂未实现，选择该协议时提示使用供应商默认、重置字段并禁用选择；后端继续拒绝不支持的协议组合。增加通用 `medium` 枚举不代表 APImart 的指定模型已经支持它，不按供应商或模型名称映射成别的档位。

思考深度与最大输出 Token 分别保存。管理员改变深度时，按所选参数进行流式、Tool Calling、结构化输出及输出预算兼容性检查；失败不创建可用模型或覆盖已有版本。较深思考可能增加延迟和 Token，不能用档位代替业务事实质量验收。

## API 与运行时分配

1. 模型表单与 API Client 使用 `reasoningEffort`；真实适配器传输既有 `reasoning_effort` 字段，并从 `capabilities` 还原已保存值。
2. 创建/更新 API、模型服务和兼容性测试共用该参数；成功后保存到不可变模型版本 `capabilities.reasoning_effort`。
3. API 更新省略字段保留已有配置；显式 `provider_default` 在新版本移除覆盖。密钥继续只写，不回显。
4. 普通推理、压缩及容量计算读取 Run 固定的 `model_id + model_revision`。修改设置影响后续消息，不改变已开始的 Run。
5. API/OpenAPI、JSON Schema、生成的 Go/TypeScript、真实适配器与 mock 使用相同档位。mock 测试只是前端工程验证，不证明供应商支持。

现有权限由企业模型管理域控制，普通用户的会话模型选择规则不变。详见[模型治理](../08-model-and-sandbox-management.md#思考深度)。
