## 1. 结论与范围

现有三元工具、领域服务、查询引擎、Workspace、Preview/Commit、共享模板与宿主交互继续复用。主要补齐“业务问题 → 资源身份 → 能力/来源 → 指标或仪表盘 → 查询/操作 → Chatbox 证据”的连接。

| 项目             | 当前基线                                                                   | Plan11 目标                                                                                     |
| ---------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 自有顶层模型工具 | 最多 9 个，另加 N 个当前会话客户 MCP 工具                                  | 不新增顶层入口，仍最多 9+N                                                                      |
| 自有业务工具     | 130 个，11 类                                                              | 新增 observe 类的 3 个工具，合计 133 个、12 类                                                  |
| 现有业务契约     | 三信号查询和仪表盘列表缺少统一类型/来源导航                                | 原八项再补作者目录输出及草稿/发布显示单位校验，共十一项                                        |
| 三元工具输入     | search(category)、describe(category,name)、invoke(category,name,arguments) | 保持字段结构，只扩展 category 枚举及契约版本                                                    |
| 工具导航元数据   | 标题、描述、示例等                                                         | 增加 resource_types、signals、operation_kind、result_kind；它们是输出说明，不是三元工具查询参数 |
| 观测目录         | Plan10 门户已有资源、指标/字段目录与推荐语句                               | 领域服务同时服务门户与 Agent                                                                    |

130/133 只统计模型可发现的自有业务入口，不含隐藏 Commit，不含客户 MCP；四个 Workspace 工具、connect、request_user_input 与三个元工具属于顶层。详细基线与清单见第 01、09 篇。

## 3. 不变的边界

- 保留分类完整列举，不给 tool.search 增加模型猜测的关键词查询或静默 Top K 裁剪。
- 自有业务工具仍先 Search、再 Describe、后 Invoke；其他工具结果中的名称引用不代替 Schema。
- 工具分类、元数据、推荐语句、资源关系和 @ 引用都不授予权限。
- 查询执行、资源管理、采集配置和远程执行复用原领域服务；不新增平行资源库、查询引擎、微服务或每种中间件一套工具。
- 框架认证完整的小结果可直接分析；大结果/截断/完整性未知须读取封存并交付Workspace的原件；模板与模型读取共享同一份事实和完整性信息。
- 变更继续执行当前 request_approval/full_access、MFA、企业审批及 PendingAction 规则；计划与用户问答不自动确认。
- 模型治理的私有数据域、客户 MCP 接入边界、人工终端票据和敏感字段保护保持现状。
- 桌面 Web、中英文、深浅色是验收范围；共享 UI 放在 @argus/ui，样式使用 design tokens。

## 4. 需要显式设计的变化

“普通诊断读取仪表盘后，不自动收窄整个 Run 的工具范围”改变了原 Dashboard Acquire 策略。原因是跨指标、日志、链路、告警的诊断需要持续组合工具。候选实现已将已获取的仪表盘与任务范围分别记录；专门的仪表盘分析继续限定已发布查询。综合诊断、专门分析和显式退出限制的三个真实模型场景已有通过证据，完整状态/授权/恢复矩阵仍按第 02、05、08 篇收齐，当前未正式部署。

## 5. 实施与评审方式

先复核缺口并统一注册/依赖构造，再接入发现目录和查询契约，随后改进会话体验与组合诊断，最后做完整真实验收。每个任务分别记录 implemented、component_verified、e2e_verified、real_model_verified、deployed，不能用“有路由”“有模板”或回放通过替代业务闭环。

文档计划已交付，用户随后授权整体实施。模型路由提示、推荐查询优先级和分类粒度仍需真实模型比较后定稿；默认候选方案和不同选择的代价已写入设计讨论，不把候选代码与受控测试当作已部署或真实模型已通过。
