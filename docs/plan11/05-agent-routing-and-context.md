# Agent 发现、任务范围与证据流程

## 1. 模型怎样快速找到工具

初始系统提示使用同一份双语分类导航，只说明：找对象/数据字典用 observe，管理对象用领域分类，执行查询用三信号或 dashboard，事件处理用 alert，文件/计划用 workflow。具体 Schema 在 Describe 获取，不将 133 个完整 Schema 注入 tools 参数。

服务端提供当前可用顶层工具、Workspace 状态、任务范围、服务端时间与剩余预算。权限决定实际列表；无工具和后台不可用是不同原因，模型不能根据某个目录为空猜用户无权限或资源不存在。

推荐推理次序：

1. 明确用户想获得的结果：定位、查询、分析、配置修改、远程执行或文件交付。
2. 利用当前已授权对象引用；只有缺少身份时再发现。多候选且无法确定时询问用户。
3. 按需要读取来源/能力、目录和 Schema；每个后续引用仍按协议先 Describe。
4. 冻结资源、来源、时间和筛选，执行有界查询或预览。
5. 读取实际结果与完整性；大结果交付 Workspace 后分析，不以工具成功代替分析完成。
6. 判断证据是否足够，必要时补查；最后给出结论、范围、证据、未完成项及可执行下一步。

这不是每次必须执行六类工具的固定工作流。已知信息可以复用，权限、Schema 版本和证据有效期必须重新验证。首次 Search/Describe 往返是协议成本，不为了减少轮数允许模型猜 Schema。

## 2. 任务范围与仪表盘对象分离

当前 Acquire/discoveredSnapshot 把获取仪表盘映射为 analyze 模式，业务 Policy 随之收窄。目标设计把两种事实分开：

| 事实               | 建议字段/状态                                                        | 谁决定                                         |
| ------------------ | -------------------------------------------------------------------- | ---------------------------------------------- |
| 本轮允许的业务场景 | task_scope：general_diagnosis/dashboard_analysis/dashboard_authoring | 宿主准入的持久事实，用户可见，模型不能自行扩大 |
| 本轮已读取的仪表盘 | acquired_dashboards 及各自条件快照                                   | 既有授权 Acquire，不能决定 task_scope          |
| 执行/计划模式      | 复用现有工作模式                                                     | 用户及既有计划流程                             |
| 请求审批/完全访问  | 复用 access_mode                                                     | 用户/服务端现有策略                            |

task_scope 不替代功能权限、资源授权或审批。建议候选：普通聊天默认 general_diagnosis；用户通过明确宿主入口选择“仅分析仪表盘”或“创建/编辑仪表盘”时，写入相应范围。@ 仪表盘只提供目标提示，不隐式改变整个会话范围。

自然语言中明确要求“只能使用此仪表盘”的限制需要由宿主接纳并显示；歧义时澄清。不能仅凭模型自报的 task_scope 扩权，也不能用自由文本提示取代服务端限制。具体中文入口与自然语言约束的准入形式在 T07 定稿并真实评测。

保持既有自动分析交互：普通问题不新增强制范围选择、常驻分析范围栏或“先选模式才能提问”的步骤。用户主动要求受限分析时才在本轮摘要显示限制；宿主显式入口为可选快捷操作，不恢复已经移除的强制手选仪表盘流程。

| 场景                | 可组合能力                                                     | 继续限制                                                     |
| ------------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| general_diagnosis   | 所有当前已授权领域工具，包含仪表盘、三信号、告警与现有远程流程 | 每次各自授权/确认；客户 MCP 仅已选连接                       |
| dashboard_analysis  | 已发布仪表盘取数、相关上下文、必要对象定位、Workspace 与交付   | 不开放自由指标/日志/Trace、客户 MCP 或远程命令去补未发布数据 |
| dashboard_authoring | 资源/指标目录、个人草稿、校验、发布预览、Workspace 与必要交付  | 不授予任意生产修改或内部模型治理来源                         |

专门场景中 request_user_input、计划提议、取消等交互与控制能力是否提供，沿用现有宿主约束并逐项测试；不能因为工具 Source=argus 就全部放行。旧行为中顶层 connect 与业务目录白名单的区别需整体审查，明确最终场景边界。

## 3. 防止范围漂移

- Run 准入快照持久化 task_scope 和来源；压缩上下文、Worker 重启、SSE 重连、描述缓存均从该事实恢复。
- 获取另一张仪表盘只增加对象，不能改变范围。各仪表盘独立冻结发布版本和条件。
- 收窄可立即生效；扩大专门范围必须由用户在宿主明确操作后开启新 Run，不能在正在执行的 Run 内无痕切换。
- 已在执行的查询继续绑定原范围；撤权触发实际执行/交付检查。新范围不能为旧查询补权限。
- 不给旧 Run 默认授予 general_diagnosis；恢复无法解释的旧版本时受控失败或维持旧策略。开发期可以清理自有测试数据，但不得改写业务历史的授权含义。

## 4. 查询与证据

资源/类型/名称由服务端可信目录解析；集成到来源映射由目录给出；时间从当前服务端时钟确定。用户明确条件优先，模型选择的参数与其理由单独记录，不能伪装成用户原话。

结果包含 effective_scope、source refs/版本、实际时间、partial/完整性、查询/任务 ID 和封存引用。重复查询必须是明确的新取证；已交付的 Workspace 文件与原封存事实分别标识，用户/模型修改副本不更改原始查询结果。

多信号诊断尽量冻结同一窗口，并保留各自采样/延迟。无日志、没有 Trace 和指标为零是不同事实。相关性、因果结论与待验证假设应分开，不能因为指标曲线同时变化就断定根因。

## 5. 预算与恢复

首次目录检索、分页、能力节、推荐语句解析、查询尝试和结果交付都记成本。不能通过更换工具、拆分分页或重试重置 Run 预算。达到预算后给出已完成/未完成范围，不伪称没有数据。

协议输入错误可按字段修正；权限、来源或版本变化必须重新发现当前事实。读请求的有界重试遵循服务策略；写请求 result_unknown 不自动重放，恢复应先读取持久执行状态。

查询交付失败与后端查询失败分开；只恢复既有安全交付时不重新查生产数据。缓存以主体、授权版本、资源、来源、时间、目录/工具版本隔离，不能把一个主体的描述或候选当成另一个主体的授权。

## 6. 三个端到端示例

### MySQL 健康检查

定位 production 的明确目标 → 能力显示 configured=true/effective=true，但 freshness=stale → 读取采集详情和目标指标的最后数据 → 如果只能证明旧窗口，不写“当前正常” → 有错误事实再建议排查或提出受确认的操作。没有确切故障证据时不自动重启数据库。

### 应用慢请求与数据库关联

定位应用 → APM RED/端点/Trace → 找到服务和数据库依赖引用 → 单独校验目标读权限 → 查询同一时间窗口的数据库指标/日志 → Workspace 交叉分析。若无目标权限，只报告应用证据及缺口，不泄露数据库配置，也不通过应用绑定扩大权限。

### 已发布仪表盘与综合诊断

用户普通问“分析 Redis 异常” → general_diagnosis → 找到适用默认仪表盘并查询 → 需要补充已授权日志和告警时继续相关工具。用户明确“只分析这张图” → dashboard_analysis → 缺少的证据标为范围之外，询问是否开启新范围，不能自动调用自由查询。

同名/同地址歧义沿 D33：资源 ID 决定身份，当前已授权主机/集群归属辅助区分；信息不足则询问并绑定回答的明确引用。归属未知仍是未知，不猜网络域，不以关系补权限，不引入必选分类表单。

D40 候选：collection_state 的配置/生效 Collector ID 只是身份锚点，placement_state=requires_authorized_resolution 表示 Host/Cluster 归属尚未核对。继续使用当前授权下的既有 Collector 元数据建立关联，不从标签、共同地址或 Host 在线推断；过滤范围之外的对象/环境没有被此次查询验证。

D52执行事实：每次Loop.context使用当前消息重建query_evidence.inline_original_in_context。仅当前授权Run的可信原生查询、可用且SHA/大小一致的Workspace副本、当前真实tool消息与持久认证投影严格等价时为true；历史user摘要或压缩后丢失的原文为false。true直接分析完整小summary；其余读取原件。read_status继续独立描述物理读取，inline可分析不得表述成“文件已读取”。所有结论仍核对来源、时间窗、类型/单位和采样边界；避免为简单数值答复扩写未经请求的推导或教程。

D53区分“当前有原文”和“此前完整提供过原文”：inline_exposure_verified只由成功实际模型请求的私有dispatch凭据重建，绑定查询ID/SHA/大小及provider request hash。压缩后可复用已建立事实，但inline_original_in_context仍为false，不能宣称原文仍在本次上下文；缺少原细节须read。旧认证标记、未发送/失败/未知请求均不构成历史消费。UseNumber保持历史原数值不因JSON重组变化。模型只给所需语言的业务摘要与实际证据引用，应用已有卡片由共享UI渲染，不由模型重抄。

D54导航：优先使用原件/目录的来源限定量值定义，不把通用单位警示覆盖具体定义。已定义ratio的原始利用率可按percent展示；其他来源/单位1仍需实际定义，不能凭名称猜。目录semantics与原生input_metric_semantics保持同源验证，Input定义不得套到任意派生结果。报告manifest_checksum_status=not_requested只表示未给期望SHA，不是损坏或校验失败；verified才表示与提供的期望值一致。模型最终给业务摘要和实际交付引用，避免复述校验布尔或手工时间/数值推导；未验证原因保持假设。
