## 1. 架构变化及复用范围

现有 Agent、Tool Gateway、Workspace、Action Executor、Connector 和凭据服务继续复用。新增的是「AI 提出的远程执行请求」及其固定计划，不新增独立微服务，不重建平台业务工具，也不复用人工 RemoteAccessSession 作为 AI 通道。

~~~mermaid
flowchart TD
  Agent[Agent Harness] --> Local[read / write / edit / bash]
  Local --> Workspace[离线会话 Workspace]
  Agent --> Native[tool.search / describe / invoke]
  Native --> Platform[平台领域服务与现有权限]
  Platform --> Query[有界遥测与资源查询]
  Query --> Evidence[封存结果与来源引用]
  Evidence --> Workspace
  Native --> PlatformPreview[平台变更 Preview]
  Agent --> Connect[connect 远程请求预览]
  Agent --> Plan[结构化计划预览]
  PlatformPreview --> Confirm[宿主确认 / 当前审批策略]
  Connect --> Confirm
  Plan --> Confirm
  Confirm --> Executor[确定性 Action / Plan Executor]
  Executor --> Commit[平台领域 Commit]
  Executor --> Remote[Linux / Kubernetes / Windows PowerShell 适配器]
  Remote --> Evidence
  Agent --> External[客户 MCP 既有独立路径]
~~~

Plan7 启用时模型集合为三个元工具＋可选四基础工具＋connect（如对本次主体与运行可用）＋N 个所选客户 MCP 工具。可用总数是 3＋W＋C＋N，W 为 0 或 4，C 为 0 或 1；全部自有能力可用时是 8＋N。当前实现已接入 connect；具体可用数量由本次主体／运行的实际工具集合决定，完成范围见验收报告。

connect 是新的核心执行场景入口，模型调用只创建预览／待确认请求；真实远程执行只发生在服务端消费批准之后。它不是为每个 Linux 命令注册一个 Tool，也不让模型通过 approved=true、dry_run=false 或隐藏 Commit 直接派发。

### 模型传输与工具参数校验的边界

2026-10-17 校正：兼容协议中的函数 `arguments` 是模型生成的字符串，可能不是合法 JSON；[官方协议](https://developers.openai.com/api/reference/resources/chat)要求调用方在执行函数前验证。Provider 负责调用身份、名称、完整结束信号和用量，不把参数 JSON 语法错误提前当作传输失败。Agent 在任何派发前要求参数为一个 JSON 对象，之后仍执行原 Schema、权限与审批校验；不修补、解包或默认补成可执行参数。

非法 JSON 作为 JSON 字符串写入已有 JSONB 调用账本，合法但非对象的 JSON 保留其原类型，原始协议参数同时保留在配对 assistant 事件中。结果记录为 `TOOL_INPUT_INVALID`，仅返回安全的字段／约束说明；重启恢复也先检查对象形状，不能把错误输入变成空参数执行。已派发但结果未明的记录保持 unknown，不重放。完整传输的真实用量正常记录，工具输入失败独立审计；缺少调用身份、缺少终止信号、无效用量等协议错误仍失败。公共 HTTP 参数 Schema、远程批准边界和未知结果规则不变。

## 2. 按执行场景判断能力

| 场景 | 用户确认 | 运行时边界 |
| --- | --- | --- |
| workspace | 不逐次确认 | 当前会话归属、PVC 路径、配额、离线运行环境；无生产凭据、无生产直连 |
| platform | 查询单阶段；已有业务变更 Preview／Confirm | 当前主体的功能权限、企业、显式资源授权和业务前件 |
| remote | 每次请求或固定计划批准 | 当前执行资格、具体资源、接入身份、完整请求、有效批准与当前前件 |
| external_mcp | 保留 PlanV5 规则 | 既有连接授权、启用状态、Revision、Schema 和凭据版本校验 |

这里的场景不是新的风险等级，不建立工具级、参数级或日级复用授权表。现有平台工具风险元数据可继续服务预览、审批和审计，不因本计划被删除或用于远程命令免确认。

平台正式业务变更保留确认；个人草稿、查询控制、结果导入／交付等既有明确例外沿用领域契约。平台变更仍提交到原领域服务，不迁移成 connect 命令。

模型返回的源类型、企业、资源名、确认说明和风险标签均不是可信授权事实。场景由服务端注册的工具来源确定；资源以当前主体有权访问的稳定 ID 解析，不接受任意 SSH 地址、代理地址或 kubeconfig 文本替换连接配置。

在「计划」模式中可以进行平台读取和 Workspace 分析。远程取证如确有需要，也必须经过一次确认；模式本身不授予现场读取资格。平台业务修改继续其既有 Preview／Confirm，不因列入一段自然语言计划就获得提交权限。

当前 Run 的模式快照同时进入系统指令和服务端事实。计划模式下，已经请求的修复必须通过 workflow 分类检索、详情、remote_plan.preview 形成固定计划，即使只有一步也不改为普通 connect；必要的额外远程取证仍可逐次确认。这个提示约束负责工具选择，不替代后端权限与确认校验，模式切换不改写已启动 Run。

read／write／edit／bash 与 connect 是按实际可用性提供的顶层工具，不属于平台分类目录。模型上下文的 builtin_tool_availability 仅列当前提供商请求实际携带的内置工具名，并标注 Run 启动时的 Workspace 状态；quota_unavailable、unhealthy 等原因不等于用户没有权限。不得从平台分类里没有某个工具推断该内置能力未授权。

模型流式生成的时限与获批命令的执行时限分离。模型端连接预算为 30 秒；普通 HTTP 请求总时限为 2 分钟，流式请求的预填充／响应头与正文共享最多 10 分钟总预算。父上下文取消或更短的流式截止时间优先，不会修改共享 HTTP Client 的超时设置。失败日志仅记录请求 Hash、阶段、HTTP 状态、超时标志和耗时，不记录地址、凭据、响应体或原始错误。验收中的模型预览等待对齐其他真实模型阶段的 10 分钟；目标命令仍严格使用冻结 Spec 的 timeout_seconds。

## 3. 远程执行请求

一次请求至少具有下列事实：

| 字段组 | 内容与要求 |
| --- | --- |
| 来源 | enterprise_id、actor_id、conversation_id、run_id、tool_call_id；主体由服务端填充 |
| 目标 | 明确 resource_kind/resource_id，必要的 namespace/workload/container 等定位；当前 K8s 基础授权粒度仍为 Cluster |
| 目的 | 用户可读的本次执行目的及证据引用；目的描述不是执行权限 |
| 内容 | 完整命令／脚本、解释器与参数、必要 stdin、输入文件的不可变引用及 Hash |
| 上下文 | 共享资源会话引用、命令进程代次、上下文版本、工作目录及前序批次；Q19 已确认聊天／资源／身份／解释器隔离 |
| 身份绑定 | 服务端解析的接入身份、凭据引用与版本、执行路由／Connector 代次，不含给模型的凭据原值 |
| 限制 | 超时、输出大小和资源预算；值必须通过服务端上限校验 |
| 批准事实 | PendingAction、内容 Hash、授权版本、有效期、批准主体和审批策略 |
| 执行事实 | execution_id、幂等关联、派发状态、输出引用、退出状态、错误与采样时间 |

物理上的一行可以包含多个操作、管道或嵌套解释器。因此批准对象是完整请求，不能按首个单词、前缀或简单换行截断后授权剩余内容。

命令静态分析只辅助语法校验和审核。未知语法不能被标记为只读／无风险；不因为解析得到较低风险就跳过用户确认。批准任意脚本不等于保证已列出其全部副作用。

### 单次执行流程

1. Agent 调用 connect 提交候选请求。
2. 服务端验证主体、企业、资源、执行权限、身份可解析性、参数及输入文件，产生冻结预览。
3. 宿主显示实际目标、身份、完整内容和影响说明；用户确认／取消。
4. 确认服务验证版本、当前权限、有效期及既有附加审批要求；记录批准事实。
5. 确定性执行器再次校验，创建有持久状态和幂等标识的远程任务，再派发到资源适配器。
6. 结果持久化并导入当前 Workspace；Agent 可继续分析，下一次远程请求重新确认。

连接、隧道和同一资源的 shell／PowerShell 会话可以复用；Q15 明确批次之间保留目录、变量等进程状态。用户批准的请求不会变成模型可自由发送后续输入的授权，新的 connect 批次仍须确认。SSH/PTY 等人工通道的票据不进入此流程；底层进程／流组件可复用，但 AI 会话需独立批准与回执协议。

每次请求可以包含一批完整指令，不按物理换行决定执行／授权边界。批准绑定批次内容及预期上下文；同一共享命令进程不得并发插入其他请求。会话范围按 Q19 固定；失效时按 Q21 暂停、分析恢复方案、确认新增命令并验证后续执行前件，见[共享会话设计](./07-shared-sessions-and-file-transfer.md)。

## 4. 计划与卡片

计划是单独持久化、版本化的领域对象，可复用 PendingAction 作为批准入口，但不能仅把多个独立确认卡合并显示就声称具备批量执行能力。

建议领域对象为 RemoteExecutionRequest、ExecutionPlan、PlanRevision、PlanStep 和 PlanExecution；是否拆表由 T01 决定。至少需要以下职责：

- 计划版本：目标说明、证据引用、展示分组、有序步骤、内容 Hash 和当前状态。
- 展示分组：描述与 step_id 列表，不具有额外执行权。
- 步骤：完整远程请求、固定目标、依赖／前件和状态；按 Q16 只串行执行，不并发派发同一计划的不同目标。
- 执行实例：批准的计划版本、创建者／批准者、实际执行步骤、结果及未执行原因。

计划预览通过平台的计划领域服务准备；具体 workflow 类业务工具名称在 T01 固化，不再新增若干顶层解释器工具。单次 connect 和计划步骤必须共用请求验证、身份绑定与派发服务，防止两条路径规则不同。

模型的 Markdown 是说明材料，不能是执行解析入口。卡片和执行器均使用同一份结构化计划；服务端重新生成权威命令展示，不采信模型伪造的「已授权」「安全」等文本。

### 一次确认的范围

- 一次确认覆盖这一计划版本中全部列明的具体请求。执行这些步骤时不再逐条弹出确认。
- 计划中预先列明的远程验证命令也在批准范围内；执行后新增验证命令仍是新的 connect 请求。
- 不包含未来生成的命令、未列明的机器、客户 MCP 调用或其他平台变更的隐式授权。
- 修改目标、命令、脚本输入、执行身份或安全相关条件，产生新版本并使未开始的旧批准不可继续使用。
- 任意失败／未知状态不触发模型自主换命令。需要新动作时生成新请求／新计划。
- 多资源操作不是全局数据库事务；部分成功要显示实际发生的变化，不能声称已自动恢复。

### 修改意见

卡片主要展示「描述＋命令片段」并提供确认执行与修改意见输入。意见是用户的新需求，不是授权，也不直接修改已经批准的对象。

新版本建立后，旧卡片必须显示已替代或不可执行。当前 PendingAction 取消可能终止等待它的 Run，实施时必须新增明确的 supersede／修订恢复语义，不能用旧 cancel 路径误杀修改后的任务。

Q18 已确认：批准后后台继续，关闭页面、断线或切换模式不构成用户取消。原提交／确认执行按钮切换到执行状态并提供可点击的停止入口；执行中不能只显示不可操作的忙碌按钮。刷新后从服务端恢复状态。

用户点击停止后，服务端记录停止请求并阻止剩余步骤启动，对当前请求执行取消处理。UI 区分执行中、停止中、已停止和停止结果未知，不能将请求受理冒充远端已经终止。正常完成、失败、超时和撤权仍按原规则转换；已经发生的修改不自动回滚。运行中修改执行内容仍须新的预览／批准，不能因页面继续编辑而静默改变已批版本。

## 5. 权限、身份与凭据

执行必须同时满足当前企业／用户状态、执行功能权限、明确资源授权、有效确认及既有附加审批、当前资源身份与前件。看得到资源不等于能远程执行；确认不补齐缺失权限。

主机使用接入账号的既有 OS 权限，K8s 使用资源接入身份的既有 API 权限。本计划不自动提权，不额外创建用户，也不因角色名看似普通就保证权限较低。公开预览应准确展示实际身份。

### 实施前差异（历史基线）

下列差异记录 Plan7 实施前的接入条件。T03 已新增持久化执行身份、SSH 接入事实解析、Windows SID 复验，以及 kubeconfig／ServiceAccount 身份绑定；缺少可靠账号绑定时仍返回不可用。当前实现入口为 `internal/remoteexecution/identity.go` 与 `runner/manager.go`，实机范围见[验收报告](./09-acceptance-report.md)。

- SSH 安装账号保存在 Credential／接入 Operation 中，Host 稳定对象没有完整的执行身份绑定；正常 Connector 的服务身份与安装账号不同。
- 当前 Linux SSH 接入预检要求有效 UID=0，因此通过现有预检的接入账号具备 root 级权限；执行时仍需复验实际身份，不得在预览中错误显示为受限账号。
- manual 主机没有 SSH 登录账号可继承。缺少可靠身份绑定时必须明确不可用，不能暗中选 root、安装进程用户或 Connector 用户。
- in-cluster Kubernetes 使用既有 Pod ServiceAccount；不是所有资源都有上传的 kubeconfig。
- Windows 现有 Connector 运行于服务身份，人工 ConPTY 并未自动切换为接入登录账号；不能以已有 PowerShell 终端为由声称 Plan7 身份绑定已具备。

T03 必须给出覆盖正式接入路径的解析契约；如果无法在已确认「沿用接入身份」边界内完成某条路径，记录具体缺口再讨论，不擅自新增账号管理模块。

### 适配器约束

- Host：新增类型化、绑定批准事实的后台命令负载；结合现有 mTLS、Connector ID/epoch、凭据租约、过期与持久结果，不借用人工终端。
- Windows：首期新增 PowerShell 执行适配，探测并冻结解释器与版本，正确处理编码、脚本异常、非终止错误及原生程序退出码，验证超时／停止时进程树处理和真实回执。传输如采用 EncodedCommand，卡片仍展示获批的 PowerShell 源码，不只显示 Base64。不能自动切换成 cmd 或复用 ConPTY 冒充单次请求执行器。
- 共享会话：新增受控 Bash／PowerShell session/runtime，保持获批批次之间的状态；普通 stdout 提示符不能作为可信完成消息，需命令批次身份、序号及执行监督端回执。
- Kubernetes：区分 API／kubectl 执行上下文与进入 Pod 的 exec，冻结目标 Cluster 及必要子资源定位。现有只读 List/GetLogs 不自动成为通用执行能力。
- 实施补充：in-cluster／via_bastion 沿已有 Connector 通道；direct-only kubeconfig 没有 Connector，因此复用现有 Direct Executor 承载同一类型化协议，不在 Agent 或 Workspace 中读取连接凭据。两条路径共用 Kubernetes 适配器。Direct Executor 的命令、执行实例归属和心跳保存在 PostgreSQL，同一解释器代次固定实例；实例失联后已派发命令进入结果未知，未派发命令明确失败，新代次重新确认，不将未知操作重新排队。此扩展补齐既有接入路径，不新增账号管理或脚本风险解析层。
- 受控 kubectl 客户端从与项目依赖一致的上游源码编译。其 REST 配置固定为本会话的无凭据代理，拒绝 server、kubeconfig、context、impersonation 等连接覆盖；实际 API 凭据只由受信执行端代用。网络策略还需实测，不能把一个配置对象视为已经隔离。
- Pod exec 存在两层身份：接入身份决定能否请求 pods/exec；容器内程序使用容器实际 UID/GID、capabilities、安全上下文及挂载资源。预览／派发需绑定 Pod UID 与 container 定位，复验实例是否变化；不能只固定可复用的 Pod 名称，也不能把 API 身份当作容器内用户。
- 模型不能通过任意地址、context、server、kubeconfig、impersonation 等连接覆盖参数，把批准的资源改成其他资源。
- 凭据由服务端／受信适配器代用；不得将长期 kubeconfig、SSH Secret 或私有确认 Token 放入 Workspace、模型、模板或公开结果。不能只把凭据文件交给任意脚本再声称它不可读取。
- 现有 kubeconfig 安全解析约束不因新增执行而放宽。未来资源类型需要各自的协议、目标和权限适配，不能仅复用一个字符串入口就算支持。

资源 ID 能绑定本次执行落点，不能证明任意脚本不会从目标机器访问其他网络资源。运行时账号、网络、凭据和操作权限仍是实际边界；若需要限制脚本的所有间接目的地，必须有对应执行环境控制，不能把命令解析或前缀匹配当成该控制。

平台托管连接凭据和私有批准 Token 的隔离是必须实现的边界；目标主机／容器自身已挂载且执行账号可读的敏感内容属于另一层风险。应明确可读范围和实际脱敏能力，不能以平台 Secret 未下发为由，承诺任意脚本的输出永远不含目标环境的秘密。

### 隧道与文件输入输出扩展

用户要求工具封装隧道与文件传输，减少模型生成 SSH/scp/编码命令的负担。现有 Connector 长连接可以复用；现有安装 Artifact 下载和文件传送并非通用 Workspace↔远端文件服务。

Q20 固定使用 Workspace 专用 input 与目标 input/output 目录，由平台扫描并自动形成清单，不要求 AI 枚举文件，也不传整个 Workspace。输入在预览时封存字节，批准后传入目标独立暂存目录；输出在执行结束后收集并记录实际 Hash 和来源。目录只简化交互，大小／路径／完整性／来源权限／半成品／重传与取消仍须有契约；见[共享会话与文件传输](./07-shared-sessions-and-file-transfer.md)。

文件重传不能引起命令重跑；隧道恢复也不证明原解释器仍存在。对原会话的恢复需对账并核对代次，实际上下文丢失按 Q21 处理，不能通过重放已执行修改来重建状态。

## 6. 状态、重试与恢复

状态名为设计草案，正式枚举在 T01 固化：

~~~text
draft → awaiting_confirmation → ready → running → succeeded
                    ↘ cancelled / expired / superseded
running → failed / partial_failed / result_unknown / stopping / cancelled
running → paused_for_recovery → awaiting_recovery_confirmation
~~~

计划、步骤和批准状态分别保存。PostgreSQL 是唯一业务事实来源；事务／条件更新与 Outbox 防止双确认、确认取消竞态、并发 Worker 和重复派发。Redis 可加速，不持有唯一批准状态。

网络发送、远端副作用和本地落库无法天然组成一个原子事务。命令丢失回执／执行器崩溃时，先记录 result_unknown 并对账，不盲目重试。已有命令结果缓存不能被描述为任意操作 exactly-once 的保证。

已批准计划在每一步派发前都重查相关身份、资源、权限和计划前件。服务端短期租约可以逐步签发；不能将一次 UI 批准转成模型持有的长期执行 Token。卡片确认有效期和执行中租约是不同概念，具体上限在 T01 固化，不恢复旧的 24 小时免确认规则。

权限撤销后不启动未执行步骤；已经运行任务的取消结果应单独记录，不能承诺撤权能够撤回已发生的副作用。Q18 规定仅明确点击停止／取消才构成用户主动中止，页面生命周期不触发取消；这不影响撤权、超时和失败等系统保护状态。

Q21 的恢复暂停保留已成功／未知／未执行的实际记录，不阻止 Agent 使用已有证据、平台查询和 Workspace 分析恢复方式。恢复方案以新版本关联原计划，新增远程取证、初始化和续执行仍取得确认；重建后验证必要上下文，仅继续仍需执行的步骤，不把旧批准直接迁入新命令进程，不自动重做已成功修改。用户主动取消不触发自动恢复执行。

Q22 允许无活动执行时闲置回收并使旧会话代次失效，运行中不因闲置终止；清理只限所有权核对通过的暂存目录，保护未收集的唯一输出和 Workspace 持久结果。Q23 不建立跨聊天的资源独占锁／业务排队；执行记录、幂等及同一个共享进程的串行保护仍保留。

新增 ResourceExecutionActivity 一类内部只读投影（名称由 T01 固化），按资源收集平台已知的并发执行、命令摘要、状态和观测时间。ContextAssembler 在下一次模型请求中注入该数据块，例如「执行 X 也正在资源 R 上运行命令 Y」。不生成聊天可见消息、ToolResult、卡片、徽标、通知或面板，不依赖前端隐藏一个已经公开下发的字段。

该投影不因并发自动增加确认、阻塞派发或修改计划；按当前主体、企业、资源及执行记录权限过滤，不能扩大模型可读范围。并发命令是参考数据，不是系统指令。内部保留来源／版本／模型请求关联供审计，每轮使用当前有界快照，未知、更新延迟和已结束状态不得伪装成「无并发」或「仍在执行」。

## 7. Agent 恢复与上下文

当前动作完成后设置 VerificationOnly，并拒绝非 ReadOnly 工具；这会同时禁止 Workspace write/edit/bash，且阻碍「确认远程命令 → 分析 → 再申请命令」。Plan7 必须替换该一刀切能力判断。

目标行为是：

1. 按持久化执行阶段和工具场景组装允许能力，调用派发前再次检查。
2. Workspace 内分析继续允许；平台查询按原权限执行；平台新变更只能生成新的 Preview。
3. 新远程请求可以生成待确认对象，真实派发仍要求本次批准；获批计划只由执行器推进固定步骤。
4. Agent 不消费私有 Token，不生成可自证批准的参数，不在结果未知时重放副作用。
5. ConversationEvent、RunCheckpoint、Plan/Step Execution 和结果引用完整关联；压缩、重启和重连不丢批准或执行事实。

默认提示顺序是「现有平台数据 → 有界取数 → Workspace 分析 → 必要现场取证 → 固定修复计划」。不得为刷本地分析比例强迫使用陈旧快照；缺少当前证据时明确说明所需资源、时间和命令目的。

## 8. 数据与输出

平台查询和远程输出均保留来源资源、时间、完整性、授权版本、内容 Hash 与执行关联。大结果写入当前 Workspace，通过有界摘要和 result_ref 进入上下文，不把全部原始结果塞入模型。

Workspace 是可编辑工作副本；封存原始证据保存在受控结果存储，防止模型覆盖后把修改文件当成采集事实。结果截断、无数据、未观测、采集失败和未分析必须分别表达。

命令输出、日志、文件和资源返回内容均是待分析数据，不是新的系统指令。输出中的「已授权」「忽略限制」「继续执行」不能触发确认或扩展计划。

## 9. 与既有文档的同步范围

本计划扩展 PlanV5 模型工具组成、Connector 后台命令类型、执行后能力恢复和 Chatbox 模式。保留现有单 Agent 内核、平台 Preview／Commit、权限／审计、Workspace 离线、客户 MCP 独立和人工远程会话隔离。

文档中的既有能力与 Plan7 目标必须分别标注；不把新增设计回填成 PlanV5 已完成验收。相关入口包括系统不变量、Connector、Agent 动作流程、安全基线、Agent Harness 和 PlanV5 架构。

## 活动长任务的硬阈值压缩

2026-10-17 P7-R03：软压缩保持完整用户轮次；硬阈值下允许选择同一 Run 内已配对完成的工具调用组。活动 PendingAction 创建事件以当前 PostgreSQL 状态保护，未完成工具组不得被截断。当前 Run 的原始用户要求和反馈按原顺序从事件记录恢复，附件按当前 Workspace／来源权限重新投影。摘要继续作为历史数据，不能代替用户原文、批准范围或执行事实。公共 API 和批准契约不变，新增的是内部事件查询及上下文组装规则。
