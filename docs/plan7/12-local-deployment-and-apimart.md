- 真实模型完成遥测取数及 Workspace 分析，现场取证、原计划、反馈修订和第二版远端计划执行均有实际记录。
- 此轮最终失败，不能当作整体通过：一次推理在响应头前发生传输错误（HTTP 状态 0，约 5 秒，未取得用量）；模型后续继续，但修复后的分析最终以 `CONTEXT_COMPACTION_FAILED` 结束。摘要模型调用本身成功，不能将此误写为摘要 JSON 或模型协议解析失败。
- 失败轮证据：`build/plan7-evidence/plan7-apimart-20261017-r01`。原 20 个工作负载及 9 个 PVC 的身份、绑定与健康恢复核验通过。本地业务尚未升级。

## P7-R03：活动长任务压缩

源代码复查和确定性回归复现两个限制：旧策略只能选择当前用户轮次以前的边界；当前 Run 的原始要求、反馈一旦落入摘要范围，重新组装时只读取切点以后的用户消息，可能丢失其原文。

修复采用完整工具调用组作为硬阈值的补充切点，并从事件记录保留当前 Run 的原始要求及修订。附件重新验证，活动审批仍保留在切点以后，批准和执行事实继续由 PostgreSQL 生成。没有提高上下文门限、放宽用量条件或把摘要当成批准。

新增回归覆盖工具组配对、活动审批、原始要求／反馈的顺序及附件失效，并通过 PostgreSQL 与真实 HTTP 测试服务验证硬阈值压缩、预算恢复、继续任务和原事件保留。新冻结版本须重新运行完整门禁后关闭 P7-R03。

## 部署准备

已保存原 Helm values、资源与凭据标识、数据库备份；候选镜像按不可变摘要复制到现有本地 Registry。当前等待修复版本验收，不把 R01 候选或其成功子项作为新版本发布通过。

部署采用保留 values 和数据的升级，涵盖 Backend、Web、MinIO、Workspace、Egress、Collector 和 remote runtime；同时更新当前 Connector／Collector 分发制品。既有远程主机上的安装程序不自动替换。

R02 已切换为正式 Web 构建配置：移除验收构建中的测试出口地址覆盖，并在首次主浏览器测试前完成受控镜像滚动；源码指纹未变。新的 Web 摘要为 sha256:51a2ed8b5f9059e04144ce5be76cc82fea8f3d4df38651934744d3641fb2037a，后续 18 项主浏览器使用该镜像。正式发布脚本会核对这一切换证据与最终候选摘要，不能把旧的测试配置发布到业务环境。

## R02 与 P7-R04：计数口径

R02 的 16 次实际 Agent 模型调用均成功且有提供方用量；主浏览器 18 项通过，但整体仍失败。模型正确计算 CPU 最小／最大／最后值，却将 13 个采样点写成 records=13；原始文件只有 1 条序列，因此 records 应为 1、samples 应为 13。旧结构化报告说明只写了“实际记录数”，没有明确区分序列和点。

P7-R04 在实际系统提示词及报告字段说明中统一 records／samples 的定义；新增回归分别验证一条／多条序列及各自多个采样点。原始文件 Hash、统计计算和结论比较条件完全保留，不归一化错误答案。R02 已失败退出并恢复原 20 工作负载及 9 PVC。

后续版本同时将正式 Web 构建策略纳入 Plan7 验收器并自动存证，禁止混入测试出口覆盖；构建回执必须与实际验收镜像匹配。当前待运行 R03 完整验收，具名检查增加到 104。

## R03 结果与独立发布回归

R03 未通过：初始遥测任务超过既定十分钟窗口；此前一次模型调用在 HTTP 200 后发生流读取或事件处理错误，耗时约 132 秒，现有有界日志无法区分具体底层原因，不能单凭此将问题归因于提供方或平台。诊断时有 17 次已成功、1 次失败及 1 次未完成的模型调用，用量不完整。失败轮保留为失败，不提高超时上限或改写用量条件。

本次 APIMart 三轮实测不能据此判定完整流程可用。为完成用户同时要求的本地部署，独立发布回归 `plan7-release-20261017-r04` 使用此前已获授权的 GLM-5.3，继续采用同一冻结源码及完整门禁；它的结果与 APIMart 测试分开记录，不能用于宣称 APIMart 通过。

临时 APIMart 密钥的受保护加密副本已经过路径／归属核验后删除；本轮 460 份证据及日志扫描没有明文密钥匹配。当前发布回归使用既有 GLM_API_KEY 环境引用，不持久更改原业务模型配置。
